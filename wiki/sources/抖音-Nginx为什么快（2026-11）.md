# 抖音-Nginx为什么快（2026-11）

## 核心观点

**Nginx 的起点不是"做一个 Web 服务器"，是解一道 C10K 的题：一台机器怎么同时接住一万个连接。** 视频用一组 12 核 Linux 上的对照实验，说明"一连接一进程"的模型为什么在一万个慢连接面前必然崩掉，而"一个 worker + epoll + 非阻塞"为什么能全接住。

一句话结论：**Nginx 快的本质不是代码写得快，是把"等待"从进程里剥离出来**——连接便宜、进程昂贵，只要让两者不再一一绑定，容量就不再由进程数决定。

## 关键内容摘要

### 问题模型：慢连接把昂贵资源钉死

- 传统做法是 Apache `prefork`：来一个连接派一个进程，守着它直到断开。
- 一连接一进程的致命处：**连接的存活时间 = 进程的占用时间**。抓一个进程 8 秒，真正读数据只用了 0.16 毫秒，其余全在睡觉。
- 慢连接的三个来源：弱网手机、开着不关的页面、故意慢慢挤数据的攻击（slowloris 类）。

### 对照实验（12 核 Linux，1 万个每 5 秒才发一行的慢连接）

| 方案 | 进程数 | 内存 | 新请求结果 |
|---|---|---|---|
| Apache 默认 | 上限 256 | — | 试 20 次，0 次进入 |
| Apache 强行开到 1 万 | 10001（1 万个 worker + 1 个管理） | 1.1 GB | 仍全部进不来 |
| Nginx | 2（1 master + 1 worker） | 112 MB | 59 次全部进入 |
| Caddy | 1 进程（goroutine） | 212 MB | 全部进入 |

- Nginx worker 抓 3 秒：醒了 1032 次，每次平均拿到 6 个连接，**没有一次空手**；整机 CPU 只忙 2%。
- 纯空闲连接 1 万个：Nginx 只多占 5.6 MB，Apache 要 1.5 GB。

### 技术路径：select/poll → epoll → 非阻塞

- `select` / `poll`：每轮把所有连接交给内核逐个查，O(n) 空转，一万个查一圈大多数白查。
- `epoll`：连接**只登记一次**，有数据的由内核放进就绪列表，进程只看这张列表。
- 非阻塞：只来半行就先记下，转身处理别的连接，从不干等。
- 结果：**一个连接只占一小块内存，不占一个进程**——这是容量从"进程数"换成"内存与 fd 数"的关键一步。

### 进程模型：master / worker 与端口共享

- **master 不处理请求**：读配置、开端口、管 worker，挂了就补。
- **端口只开一次**：master 先 listen 8080 再 fork，子进程天生继承同一个监听套接字（8080 只有一行 LISTEN，多个进程共用同一 fd）。
- **或 `reuseport`**：`listen 8080 reuseport`，每个 worker 各开一个监听套接字，`ss` 里变成 N 行 LISTEN，由内核分发。
- **一核一 worker**：一个进程同一时刻只能用一个核，12 核就开 12 个。
- **reload 不断连接**：master 校验新配置 → 起新 worker → 旧 worker 不再接新连接 → 处理完手上请求再退出。实测 40 MB 下载过程中 reload 3 次不中断、字节不差；改成"先停再启"则断在 17.7 MB。

### 为什么必须放在后端前面

- 后端常见模型仍是"一连接一进程/线程"，例如 gunicorn 默认的 `sync` worker。
- 实测：4 个 gunicorn worker 直接吃 1000 个慢连接 → 新请求 10 次全部超时；前面加 Nginx → 慢连接停在入口、请求头收齐后才转给后端 → 29 次全部进入。
- **gunicorn 官方文档自己就写着"强烈建议放在代理服务器后面"，且强烈建议 Nginx。**

### 它不是唯一的答案

- Apache 后来也有事件驱动的 `event` MPM。
- Caddy（Go）：每连接一个 goroutine，起步几 KB，底层等数据仍走 epoll。
- Cloudflare：早年靠 Nginx，自称体量已超过它，2022 年起自研 Pingora。

## 视频说法与事实核对

| 视频说法 | 核对结果 |
|---|---|
| Nginx 2002 年由伊戈尔·赛索耶夫开始写，为解 C10K | 基本属实。开发始于 2002，2004 年公开发布；C10K 是 Dan Kegel 在 1999 年提出的经典命题 |
| Apache prefork 默认最多 256 个进程 | 大致属实（依构建与配置而定，`MaxRequestWorkers` 常被设为 256），但"默认"不是恒定值 |
| 1 万慢连接下 Apache 吃 1.1 GB、Nginx 112 MB、Caddy 212 MB | 单机单次实测，能说明量级差异，**不可当基准引用**；与内核参数、连接状态、编译选项都有关 |
| 空闲 1 万连接：Nginx +5.6 MB / Apache 1.5 GB | 同上，量级结论成立，具体数字依赖测量口径 |
| `ss` 里 8080 只有一行 LISTEN，13 个进程共用 fd | 原理正确（master 先 bind+listen 再 fork，子进程继承 fd）；`ss` 的显示方式随版本不同 |
| `reuseport` 每个 worker 各开监听套接字 | 属实，Nginx 1.9.1+ 支持 `listen ... reuseport` |
| reload 不中断下载 | 属实，这是"优雅退出（graceful shutdown）"的标准行为 |
| gunicorn 文档强烈建议放代理后面、且建议 Nginx | 属实，gunicorn 部署文档明确建议置于代理服务器之后 |
| W3Techs：Nginx 30.1%，Cloudflare 33% 排第一 | 数字需按 W3Techs 当期页面核对；"Cloudflare 服务器份额高于 Nginx"这一判断在近年统计中常见，但**具体百分比不可直接引用** |
| Cloudflare 2022 年自研 Pingora | 部分属实：2022 年公开宣布自研，Pingora 于 2024-02 开源 |
| Caddy 用 goroutine，底层仍是 epoll | 属实，Go runtime 的 netpoller 在 Linux 上由 epoll 支撑 |

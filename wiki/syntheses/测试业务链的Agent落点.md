# 测试业务链的Agent落点

> 以“需求 → 策划 → 用例 → 执行 → 报告”这条链为例，判断每一段该用 LLM、workflow 还是 agent，以及产品形态为什么不是对话框。

## 问题 / 主题

测试业务链上，哪些环节能通过 agent 提效？应用形态应该是网页对话框、桌面 MCP，还是别的形式？

## 结论

- **越往“执行”走，越符合 agent 的定义；越往“策划”走，越依赖数据而不是模型。**
- 形态上，正确答案基本不是对话框。**对话框是入口，不是形态**；agent 应该活在业务流程、单据系统和 CI 流水线里。
- 五个环节的判据只有两条：路径可枚举吗？有可验证反馈吗？详见 [[Agent适用性判据]]。

## 五环节总览

| 环节 | 路径可枚举 | 有可验证反馈 | 该用什么 | ROI | 落地难度 |
|---|---|---|---|---|---|
| 需求分析 | 高 | 弱（对不对要等上线） | 一次性 LLM 调用 / 轻 workflow | 中高 | 低 |
| 测试策划 | 低 | 极慢（一个版本后才知道） | Copilot（人主导）+ 知识库检索 | 高 | 高 |
| 用例生成 | 中 | 中（覆盖率/缺陷检出率可测） | Workflow 起步，接代码库后升级为 agent | 最高 | 低-中 |
| 测试执行 | 低 | 强（通过/失败/截图/日志） | 必须是 agent | 高 | 中-高 |
| 报告 | 高 | 中 | Workflow | 低-中 | 低 |

## 逐段拆解

### 1. 需求分析：不需要 agent，但价值被低估

AI 能做的：从 PRD、会议记录、Jira 单里抽出需求点，标出歧义和缺失，生成验收标准（AC），列一份“要问产品的问题清单”。

为什么不是 agent：这是一次“读长文档 → 结构化输出”，没有循环的必要。硬套 agent 只会更慢更贵。

真正的价值：需求歧义是整条链路里最贵的问题。一个含糊的验收标准，会在用例阶段放大成几十条错用例，在报告阶段变成“到底算不算 bug”的扯皮。越早发现越省钱，而长文本理解 + 结构化输出恰好是 LLM 最擅长的。

唯一的坑：它会编需求。生成内容必须标注原文出处页码，让人能核；没有溯源的需求分析等于给团队埋雷。

### 2. 测试策划：价值最高，但最不适合交给 agent

这一段是很多人想错的地方。测试策略不是“生成”出来的，是基于组织记忆做判断：

- 这块代码历史上出过几次线上事故？
- 这个模块谁改的、改了多少？
- 上次类似的改动，回归范围是什么？
- 这次时间只够 3 天，砍哪块？

这些信息不在模型权重里，在缺陷库、git 历史、事故复盘里。**瓶颈不是模型能力，是能不能把这些数据接进来。**

为什么不能让 agent 自主跑：它的反馈周期是一个版本。Agent 需要“做错立刻知道”，而策略错了要等线上出事才知道。没有即时反馈的环节，agent 无法自我纠正，只能是 Copilot。

正确做法：人做决策，AI 提供带证据的输入，例如“这个改动涉及支付回调，历史上该模块 6 个月内有 4 个 P1 缺陷，建议回归范围包含 X/Y/Z，依据：[链接]”。

关键认知：**这一段做得好不好，取决于缺陷库和代码库有多干净，不取决于用哪家模型。** 这是数据工程问题，不是 AI 问题。

### 3. 用例生成：ROI 最高，也最容易被做浅

为什么 ROI 最高：它处在“输入结构化（有 AC）+ 输出可验证（能执行、能算覆盖率）”的甜点上，而且人工写用例是纯苦力。

大多数人做到的是最浅的一层：贴一段需求 → 生成 20 条用例 → 复制出来 → 人工改。这只是省了打字。真正的瓶颈不是“想不出用例”，是“想不出这个系统专属的用例”。

通用智力能想到“输入为空”“超长字符串”“SQL 注入”，想不出：

- 这个接口在并发 200 时会不会死锁。
- 这个字段和另外三个模块的状态机有隐式耦合。
- 上线时这个开关默认是关的，会导致老数据走错分支。

这些只能从代码、接口定义、数据库 schema、历史缺陷里挖。升级路径：

| 阶段 | 输入 | 效果 |
|---|---|---|
| L1 | 贴需求文本 | 通用用例，覆盖率提升有限 |
| L2 | 需求 + 接口文档（OpenAPI） | 能生成参数组合、边界值 |
| L3 | 给仓库读权限，自己找上下文 | 能发现隐式约束；这是从 workflow 变 agent 的分水岭 |
| L4 | 接入历史缺陷库 | 能针对“这个模块以前怎么坏的”生成回归用例 |

到了 L3，它就必须是 agent，因为它要自己决定读哪个文件、查哪个 schema、看哪段代码，tool use + 循环才有意义。

必设约束：每条用例必须标注“可执行 / 需人工补充数据”和“来源需求条目”。不加这个约束，会得到 300 条看起来很专业但一条都跑不了的用例，这是该场景最常见的失败方式。

### 4. 测试执行：唯一天然属于 agent 的环节

这是整条链上三要素唯一齐全的地方：

- 模型做决策 ✓
- 有工具能动手（浏览器、设备、终端、DB）✓
- 有循环和强反馈（成功/失败/截图/日志）✓

而且路径不可枚举：UI 会变、环境会挂、弹窗会挡、加载会慢，这些写不进脚本。

四个子场景，ROI 差别很大：

| 子场景 | 说明 | 评价 |
|---|---|---|
| 失败归因 | 读日志、看截图、复现，判断是产品 bug / 用例问题 / 环境问题 | ROI 最高，建议第一个做；反馈信号极强 |
| 自愈 | 元素选择器失效，自己定位新的 | 高；传统 UI 自动化的头号维护成本 |
| 探索性测试 | 无预设路径，自己点，找异常 | 中；真 agent，但“找到问题”的质量难评估 |
| 数据/环境准备 | 造数据、清库、切环境 | 中；重复劳动，容易做 |

必须划一条界线：**能脚本化的，绝不 agent 化。** 稳定的核心回归路径用脚本，快、稳、便宜、可并行；Agent 只兜脚本覆盖不到的部分：新功能、易变 UI、异常场景、探索。用 agent 跑核心回归是最常见的浪费：慢十倍、贵二十倍、还不稳定。“脚本保底，agent 兜增量”是唯一算得过来的账。

#### 测试领域独有的致命陷阱：test oracle

如果同一个 agent 既生成用例、又执行、又判定通过，它会把错误的预期也判成“通过”，相当于自己出题、自己答卷、自己打分。

**预期结果必须来自独立信源**：需求文档、已确认的基线、人工确认，不能由执行 agent 自己生成。这条约束比一般 agent 场景严格得多；漏了它，自动化率会很好看，缺陷会照样漏出去。

### 5. 报告：不需要 agent，但可以换个目标

生成测试报告是纯 workflow：汇总数据 → 套模板 → 出结论。LLM 做这个又快又好，但价值有限，因为没人真的读报告。

真正有价值的是把目标从“生成报告”换成“生成决策”：

> 本次改动涉及 3 个高风险模块，新覆盖 47 条用例，其中 12 条在支付链路。建议：可发布，但需灰度到 5% 并监控 X 指标 2 小时，依据：[数据]。

这个升级需要接历史基线（上次发版什么水平、哪些指标异常过），本质还是数据问题。

## 形态：为什么对话框和桌面 MCP 都不是答案

“智能客服 vs 桌面 MCP”这个二选一问偏了。真正的判据还是：**它需要碰到什么。**

| 形态 | 能碰到什么 | 在这条链上的角色 |
|---|---|---|
| 网页对话框 | 你贴给它的东西 | 只能做 POC 和个人提效；贴需求生成用例，一次几十条就到上下文上限，结果没法落库、批量、追溯 |
| 桌面 MCP | 本地代码库、本地环境、内网 DB | 个人调试利器，不能团队化；零集成成本，但进不了 CI、没有审计、换个人就不能用 |
| 嵌进业务系统（Jira / 测试平台） | 需求单、用例库、缺陷库 | 用例生成的正解：读单据 → 生成 → 回写 → 人工审 |
| CI 流水线节点 | 构建产物、测试环境、日志 | 执行与归因的正解：失败自动触发，无人值守 |
| IDE / CLI | 仓库全文、终端 | 测试同学写和维护自动化脚本时用，性价比很高 |
| 对话框（作为入口） | 全部（背后调 workflow） | 只是 trigger，不是形态 |

核心结论：

- 可以有一个聊天框当统一入口，用户说“给 PROJ-1234 生成用例”，它触发背后一个 workflow。
- 但绝不该让用户在对话框里完成这件事。
- **Agent 应该活在流程里——流水线节点、单据系统里——而不是等人来找它聊天。**

## 三个容易被忽略的点

### ① 断点比段点更值钱

五个段之间的损耗，大部分发生在段与段之间的搬运动作上：

- 用例生成完了，谁负责录进测试管理工具？
- 执行挂了，谁去建缺陷单、填复现步骤？
- 缺陷修了，谁去回关联到需求？

Agent 最大的增量往往不是“把某一段做得更快”，而是“把上下游自动接起来”。例如：执行失败 → 自动归因 → 自动建缺陷单（带截图、日志、复现步骤）→ 自动关联用例和需求。这一条链的提效可能超过前面所有单点优化。

这也是“harness 比模型重要”的原因：连接能力来自工程，不来自智力。

### ② 数据飞轮是真正的护城河

用例被采纳了什么、被人改了什么、哪条用例最终检出了缺陷，这些记录比模型选型重要得多：

- 被采纳率 → 评测生成质量。
- 被修改的地方 → 说明模型哪里系统性想错。
- 检出缺陷的用例 → 什么样的用例真正有效。

没有这些数据，无法回答“上 agent 到底有没有变好”，只能靠感觉。

### ③ 先定义度量，再上 AI

最小度量集：

- **用例**：采纳率、人工修改率、检出缺陷数 / 千条。
- **执行**：自愈成功率、flaky 率变化、平均失败定位时间。
- **归因**：误判率（说是产品 bug 结果不是）。

## 务实落地顺序

按“ROI ÷ 难度”排序：

1. 失败归因（反馈最强、最容易验证、纯省人力）。
2. 用例生成 L1→L2（贴需求 + 接接口文档，先跑通流程和采纳率）。
3. 需求歧义检测（便宜，且能保护下游）。
4. 用例生成 L3（给读代码权限，这一步才真正需要 agent）。
5. 执行自愈（UI 自动化维护）。
6. 探索性测试（价值高但最难评估，放最后）。
7. 测试策划 Copilot（要等数据积累起来才做得动）。

不要从 6 和 7 开始：它们是最好看的 demo，也是最难证明价值的。

## 尚存的缺口 / 待研究

- 用例生成 L3/L4 的 harness 设计（读哪些文件、怎么控制上下文、怎么保证可执行性）尚未展开。
- 失败归因做到“误判率可接受”的具体方法和评测集设计缺少一手资料。
- 测试平台（Jira、用例库、CI）的集成接口与权限模型需要按实际系统确认。
- 五段的 ROI 排序来自经验判断，缺少项目级实测数据。

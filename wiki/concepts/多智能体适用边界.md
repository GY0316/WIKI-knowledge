# 多智能体适用边界

> 多智能体不是能力升级，是组织手段。它只在特定条件下划算；默认方案是单 agent + 好工具 + 好上下文。

## 结论

1. **先问“为什么要多个”**。2024 年多智能体被框架厂商炒过一轮，2025 年业界大面积回退。Cognition（Devin 团队）在《Don't Build Multi-Agents》里的核心论点是：上下文在 agent 之间传递时会丢信息，单线程全上下文的 agent 在多数任务上更好；Anthropic 的多智能体研究系统也披露，多 agent 消耗约 15 倍 token，且只在“广度优先的并行检索”这类任务上明显划算。
2. **多智能体解决的是“上下文装不下”和“任务能并行”，不是“能力不够”**。能力不够时加工具，上下文不够时加检索，只有这两条都做到头了，才轮到加 agent。
3. **多智能体 ≠ 多个 LLM**。真实系统里的 worker 大多数是确定性引擎、专用模型或人，真正需要判断力的 agent 往往只有一个。

## 五个正当理由

只有以下五类理由成立：

| 理由 | 说明 | 例子 |
|---|---|---|
| 上下文隔离 | 单个上下文装不下，或子任务互相污染 | 几何检查不需要看网表细节，SI 仿真不需要看丝印 |
| 可并行 | 子任务独立，延迟是痛点 | 6 个信号通道同时做 SI 分析 |
| 工具集差异大 | 一个 agent 带 5 个工具比带 50 个准得多 | 几何 checker 与 CV checker 的工具完全不重叠 |
| 权限/合规边界 | 不同 agent 可见的数据范围不同 | 客户 A 的板子数据不能进同一个上下文 |
| 独立视角互检 | 生成者与审查者分开，能纠错 | 整改建议生成后，另一个 agent 按工艺规范挑错 |

其中①和③最实在，⑤最被高估：互检有效，但成本翻倍，且两个 agent 共享同样盲区时毫无用处。

## 三个不正当理由

- “更像人脑 / 更像公司组织”——这是比喻，不是工程理由。
- “更强大”——通常更弱、更贵、更难调。
- “每个模块一个 agent 比较清晰”——清晰是人的感受，接缝是系统的 bug。

## 成本清单

每一条都真实发生：

- **信息损耗**：A 的发现要转述给 B，转述必然有损，这是最大成本。
- **错误放大**：一个 agent 的错觉会被下游当成事实，层层加固。
- **协调开销**：谁来汇总？汇总本身往往又是一个 agent，递归下去。
- **调试爆炸**：10 个 agent 的交互路径几乎无法复现。
- **延迟累加**：串行编排是加法，不是并行就白搭。
- **成本**：N 倍 token，收益通常不到 N 倍。

## 多智能体 ≠ 多个 LLM

真实系统里的 worker 可以是：

| worker 类型 | 例子 |
|---|---|
| 确定性引擎 | 几何 DRC、网表 ERC、规则校验 |
| 专用模型 | CV 焊点检测、SI 场求解器 |
| LLM agent | 分诊、归因、方案生成 |
| 人 | 审批、最终判定 |

所以多智能体的设计问题，本质是“任务如何分解 + 接口如何定义”，不是“多开几个 LLM”。把 DRC 做成一个 LLM agent 去调算法，只会增加不确定性和成本。判断方法：**如果一个 worker 的工作能用一句确定性的话描述完（“找出所有间距小于阈值的地方”），它就不该是 agent，该是函数。**

## 四种拓扑

| 拓扑 | 结构 | 适合 | 风险 |
|---|---|---|---|
| Orchestrator-Worker | 主 agent 拆任务 → 派发 → 汇总 | 可分解、子任务独立 | 汇总时信息失真；主 agent 是瓶颈 |
| Pipeline | A 输出 → B 输入 → C | 阶段清晰（需求→用例→执行→报告） | 其实更像 workflow，agent 只是节点 |
| 生成-审查 | 一个产出、一个挑错、循环 | 有明确评判标准（代码审查、规范校验） | 两者共享盲区时失效 |
| 对等 Handoff | agent 之间自由交接 | 客服分流这类 | 最容易退化成路由；最难调试 |

## 最典型的失效：接缝

> 分解会制造接缝，而问题恰恰集中在接缝上。

失败长这样：

```text
Orchestrator: 派 5 个 worker 检查 5 个模块
Worker 1: 我这块没问题 ✓
Worker 2: 我这块没问题 ✓
...
Worker 5: 我这块没问题 ✓
Orchestrator: 整体没问题 ✓

→ 但真正的问题在“模块 2 和模块 3 的交界处”
→ 没有任何一个 worker 负责交界
→ 全员正确，结论错误
```

PCB 上的问题尤其爱出现在边界：电源与信号的交界、地平面分割处、连接器引脚、跨层过孔。每个“模块内检查器”都认为不归自己管。

对策只有两条：

1. **显式定义接缝检查**，把它当作一等任务派给专门的 worker。
2. **扇入时做跨域关联**。这正是 triage agent 不可替代的价值：它同时看到所有 worker 的结果，才能发现“R3 的线宽警告 + VCC 网络的载流不足”是同一件事。

换句话说：**多智能体的收益不在“分”，而在“合”。分只是手段，合才是价值。**

## 采用清单

前四条命中任意两条以上，再考虑多智能体：

- [ ] 单个上下文确实装不下（不是“感觉长”，是实测爆窗）。
- [ ] 子任务真的能并行，且延迟是痛点。
- [ ] 子任务的工具集差异极大（各 >10 个且不重叠）。
- [ ] 有硬性的权限/数据隔离要求。
- [ ] 需要独立视角做互检，且有明确的评判标准。

一条都不命中，就先做单 agent + 更好的工具 + 更好的上下文工程。

## 推荐形态

结合 [[测试业务链的Agent落点]] 与 [[PCB检查的Agent架构]] 两个案例：

| 角色 | 是什么 | 为什么 |
|---|---|---|
| 调度/分诊 agent | 单个 LLM agent | 唯一需要判断力的地方：选规则、聚类、跨域关联、排序 |
| 检查 worker | 确定性引擎（不是 agent） | 要求可复现、可辩护 |
| 检测 worker | 专用模型（不是 agent） | 要求精度 |
| 规则知识库 | 上下文 / RAG（不是 agent） | 最便宜的增强手段 |
| 人 | 审批节点 | 责任边界 |

这就是“一个 agent + 一群工具”，不是“一群 agent”。工具承担了绝大部分工作，agent 只负责把工具串起来并解释结果。

## 尚存的缺口 / 待研究

- 多智能体“收益 > 成本”的临界点缺少实测数据，尤其是 token 成本与任务成功率的交换曲线。
- 接缝检查如何系统化枚举（按数据流、按物理边界、按状态机交互）还没有可复用的方法。
- 生成-审查拓扑中“共享盲区”的检测手段不足，需要评测集设计上的补充。

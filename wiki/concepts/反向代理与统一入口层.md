# 反向代理与统一入口层

## 一句话定义

在客户端与具体后端之间插入一层**对外唯一、对内可分发**的入口：外部只看到一个地址，加密、路由、缓存、限流、日志都在这层收敛，后端退回内网、只做业务。

## 详细说明

### 1. 它解决的不是"性能"，是"收敛"

直连后端在技术上没有任何问题——后端当然能自己接请求。加这一层的价值在于把**重复的、易错的、属于基础设施的活**从每个服务身上剥离出来：

| 职责 | 直连时谁来做 | 有入口层后 |
|---|---|---|
| 公网证书与 TLS | 每个服务各自配、各自续期 | 入口配一次，统一轮换 |
| 静态文件（图片/CSS/JS） | 应用进程返回，占业务线程 | 入口直接读盘返回，可加缓存与压缩 |
| 多实例流量分配 | 客户端只能连一个地址 | 入口轮询/加权，加机器不改对外地址 |
| 内部拓扑暴露 | 后端端口直接对外 | 后端藏内网，只暴露入口 |
| 访问日志与限流 | 每个服务各写一套 | 一处记录、一处限流 |

所以判断口径是：**"有没有被重复做的横切职责"**，而不是"项目多大"。

### 2. 三个触发条件（满足一个就值得加）

1. **多服务共用证书**：域名多、服务多，但公网证书只想管一份。
2. **静态与业务分离**：路径即路由，`/assets/` 走磁盘，`/api/` 走后端。
3. **后端多实例**：需要按轮询/加权分发，或需要平滑重启与灰度切流。

三条都不满足——单实例、低流量、框架自带 HTTPS 与静态返回——**直连是对的**，多一层只会多一个故障点。

### 3. 还有一条更刚性的理由：容量，而不是收敛

前两条是"收敛"：不用也能活，只是重复。这一条不同——**不加就会被打穿**。

- 后端若是一连接一进程/线程的模型（gunicorn `sync` worker、PHP-FPM、Apache prefork），**连接的存活时间就是进程的占用时间**。
- 慢连接（弱网手机、长驻页面、slowloris 式慢发数据）能用极低的成本占住极贵的资源。实测：4 个 gunicorn worker 直接吃 1000 个慢连接，新请求 10 次全部超时；前面加一层后 29 次全部进入。
- 入口层的解法是**收齐请求头再转发**——不完整的请求永远停在门外，后端只处理"已经准备好"的请求。

所以判据要升级为两级：**先看后端并发模型（同步=刚性需求），再看三个部署触发条件（异步=渐进需求）。**

### 4. 四种"入口层"不是一回事

这几个词经常被混用，实际是四个不同位置：

| 层 | 方向 | 典型代表 | 主要职责 |
|---|---|---|---|
| 反向代理 / Web 入口 | 南北向（用户→系统） | [[Nginx]]、Caddy、Traefik | TLS、路由、静态、压缩、缓存、简单限流 |
| API 网关 | 南北向 | Kong、APISIX、Spring Cloud Gateway | 鉴权、配额、插件化限流、灰度、可观测 |
| BFF | 南北向 | 自研聚合层 | 为特定端（Web/App/小程序）聚合与裁剪接口 |
| 服务网格 | 东西向（服务↔服务） | Istio、Linkerd | mTLS、重试、熔断、流量镜像 |

**判断顺序**：先问"要不要一个对外的统一入口"（Nginx 级）；再问"要不要在入口做鉴权/配额/灰度"（网关级）；再问"要不要按端做聚合"（BFF）；服务网格是另一根轴，与前三者不冲突。

### 5. 加了这一层就必须承担的代价

- **多一跳**：延迟增加、连接数翻倍，长连接与 WebSocket 需要显式升级配置。
- **超时会叠加**：入口超时、上游超时、后端超时三层必须逐层收窄，否则 504 出现时根本不知道卡在哪。
- **真实客户端信息会丢**：必须透传 `X-Forwarded-For`、`X-Forwarded-Proto`、`Host`，后端还要显式"信任代理头"，否则日志、限流、跳转全错。
- **配置漂移**：入口配置往往不进代码仓库、不做评审，成为最容易被改坏又最难追溯的一层。
- **空闲连接被掐**：代理默认会在 60 秒左右断掉空闲连接（见 [[通讯协议对比与选型]]），心跳间隔必须小于它。

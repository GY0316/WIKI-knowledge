# Agent适用性判据

> 判断一个环节该用 workflow、agent 还是确定性工具，不靠“先上再说”，靠两条可验证的判据。

## 两条判据

| 判据 | 问什么 | 决定什么 |
|---|---|---|
| 路径可枚举吗 | 步骤能不能事先写死 | 能 → 脚本 / workflow；不能 → 才考虑 agent |
| 有可验证反馈吗 | 做错后能不能立刻知道 | 有 → agent 能自我纠正；没有 → 只能人主导或 Copilot |

组合起来是四象限：

| | 强反馈 | 弱反馈 |
|---|---|---|
| 路径可枚举 | 脚本 / 确定性工具（最稳） | workflow + 人工审核 |
| 路径不可枚举 | agent（唯一真正适合的格子） | 人主导 + AI 辅助（Copilot） |

- **有可验证反馈**决定 agent 能不能自己跑。测试执行有通过/失败/截图/日志，agent 可以自我纠正；测试策划的反馈周期是一个版本，策略错了要等线上出事才知道，agent 无法自我纠正。
- **路径可枚举**决定它该不该跑。UI 会变、环境会挂、弹窗会挡、加载会慢，这些写不进脚本，才需要 agent 现场判断。

## Workflow 与 Agent

| 维度 | Workflow | Agent |
|---|---|---|
| 路径由谁定 | 人预先编排 | 模型运行时决定 |
| 模型角色 | 只负责其中每一步 | 决定流程、工具和停止时机 |
| 可靠性 | 高，可测试、可预测、成本可控 | 较低，难测试、难控成本 |
| 适用 | 步骤可以枚举 | 路径无法预先枚举 |

参见 [[AI术语分层与Agent产品形态]] 对 Agent 三条件的定义：LLM 做决策、有工具能改变环境、有循环和状态，缺一不可。

## 能力三层：参数、上下文、工具

“LLM 负责推理，其他都是工具”这个两分法少了一层，而那一层往往最省钱：

| 层 | 里面有什么 | 能怎么改 | 例子 |
|---|---|---|---|
| 参数里 | 语言、常识、推理、部分领域知识 | 换模型或微调 | “什么是短路”“DFM 大概查什么” |
| 上下文里 | 提示、示例、检索到的知识、历史 | 完全可控，最便宜 | 板厂能力表、IPC 条款、历史整改案例 |
| 工具里 | 精确计算、真实副作用、专用感知 | 自己造 | DRC 引擎、CV 缺陷检测、CAD 操作 |

判断规则只有一条：

> **这件事有没有确定性算法或权威数据源？有 → 做成工具或放进上下文；没有 → 只能留给模型。**

- 线宽 0.15mm 够不够 2A → 有公式 → 工具。
- 这块板该跑哪些规则 → 有板厂能力表 → 上下文 + 模型判断。
- “这个整改方案客户能接受吗” → 没有算法 → 留给模型。
- “这个焊点有没有虚焊” → 有 CV 模型 → 工具，但要分清这不是 LLM，是专用模型。

两个细节：

1. **“分析图片”不一定是工具**。多模态模型的视觉能力在参数里，不需要外挂；只有需要像素级精度（例如 0.1mm 的焊点缺陷）时，才该换成专用 CV 模型当工具。通用理解用模型的眼睛，精密测量用工具。
2. **工具的价值不只是扩展能力**。它还提供契约（schema 可校验）、可观测（调用可记录、可回放、可归因）、可评测（能单独测准确率）。模型会不会是概率问题，工具对不对是确定问题。

## 判据的用法

1. 先问有没有确定性算法或权威数据源。有就做成工具，别让模型猜。
2. 再问反馈是否即时。没有即时反馈的环节，不要交给自主 agent，做 Copilot。
3. 最后才问是否需要多个 agent。默认是单 agent + 更好的工具 + 更好的上下文工程，边界见 [[多智能体适用边界]]。
4. 跨环节的搬运和衔接往往比单点优化更值钱，见 [[测试业务链的Agent落点]] 的“断点比段点更值钱”。

## 尚存的缺口 / 待研究

- “有可验证反馈”如何量化（反馈延迟、信号强度、误判成本）还缺一套可操作的评估方法。
- 判据目前主要来自测试与 PCB 两个场景，需要在更多业务类型里验证，避免把领域经验当成通用规律。
- “上下文层优先于工具层”的结论缺少成本对比数据：什么时候写工具比塞上下文更划算，还没有实测。

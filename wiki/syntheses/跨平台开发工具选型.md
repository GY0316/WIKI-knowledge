# 跨平台开发工具选型

## 问题 / 主题

面向桌面、移动、Web、鸿蒙和小程序时，如何在安装包、运行性能、团队技术栈和各端适配成本之间取舍？本页适合做候选初筛，平台与兼容性以拟采用的版本为准。

## 结论

先列出必须上线的平台、最低系统版本和关键功能，再按团队现有技术栈与产品体验选出两个候选。覆盖目标平台只是第一关；能否复用插件、稳定运行和方便发布，往往更能决定维护成本。

| 开发场景 | 优先验证 | 取舍 |
| --- | --- | --- |
| 已有 Web 界面，要做 Windows、macOS、Linux 客户端 | Electron / Tauri | 更重视各端 Chromium 表现接近，先看 Electron；更重视下载体积，先看 Tauri，并测试目标系统的 WebView。 |
| 要同时交付轻量桌面和移动客户端 | Tauri / Flutter | 已有浏览器界面可先验证 Tauri；主要诉求是共享定制 UI，可先验证 Flutter。两者都要确认桌面和移动插件分别支持什么。 |
| iOS / Android 是主端，高频交互或原生 SDK 是关键 | React Native / Flutter | React 团队或重视系统控件，先看 React Native；有大量自绘界面、动画或统一视觉需求，先看 Flutter。用真机对比关键交互。 |
| Android、iOS、鸿蒙 NEXT 都必须上线 | Kuikly / uni-app x | Kotlin 团队或要嵌入现有原生 App，先看 Kuikly；Vue 团队可先验证 uni-app x。先打通鸿蒙端最难接的 SDK。 |
| 微信、支付宝、抖音等多个小程序要同步上线 | uni-app | 逐端核对登录、支付、分享、分包和发布流程。若只需微信/支付宝并同时重视 App 体验，可评估 uni-app x；若以 Kotlin 和原生 App 为主、微信小程序是补充，可评估 Kuikly 的 Beta 支持。 |

## 论证 / 对比

| 工具 | 渲染机制与平台 | 体积、性能与适配代价 |
| --- | --- | --- |
| [Electron](https://www.electronjs.org/docs/latest) | 自带 Chromium 和 Node.js，用 Web 技术开发 Windows、macOS、Linux 应用。[VS Code](https://code.visualstudio.com/docs/supporting/faq) 是可核实的例子。 | 可复用 Web 界面，浏览器层差异较少。随包分发运行时会增加基础包体，运行时应合计主进程和渲染等子进程的资源占用。 |
| [Tauri](https://v2.tauri.app/start/) | Web 前端配 Rust 核心，使用[各平台的 WebView](https://v2.tauri.app/reference/webview-versions/)，目标包括 Windows、macOS、Linux、Android、iOS。 | 不随应用打包整个浏览器，可减小应用包。WebView 的内核、版本及系统插件按端变化，要验证 CSS、输入法、媒体播放等实际能力。 |
| [React Native](https://reactnative.dev/docs/intro-react-native-components) | 用 React 声明界面，核心组件由平台原生视图承载。主线面向 iOS、Android；Windows、macOS、Web 等见[独立平台项目](https://reactnative.dev/docs/out-of-tree-platforms)，需单查生态。 | [新架构](https://reactnative.dev/architecture/landing-page)改善渲染和 JS 与原生互操作，实际提升取决于应用瓶颈。重点测长列表、手势、动画和依赖的原生模块。 |
| [Flutter](https://docs.flutter.dev/resources/architectural-overview) | 使用 Dart，主要由自有引擎绘制组件；[官方部署目标](https://docs.flutter.dev/reference/supported-platforms)包括 Android、iOS、Web、Windows、macOS、Linux。 | 共享视觉组件可减少重复适配；包体要计入引擎和资源，输入法、无障碍、系统服务、插件和发布仍需逐端验证。 |
| [Kuikly](https://github.com/Tencent-TDS/KuiklyUI/blob/main/README-zh_CN.md) | 腾讯基于 Kotlin Multiplatform 推出，可共享 UI 与逻辑，在 Android、iOS、鸿蒙使用平台渲染实现。官方还列出 Web、微信小程序（Beta）及 macOS（Alpha）。 | 鸿蒙与微信小程序都有明确的接入路径。评估时分别核对渲染器、组件覆盖、第三方 SDK 和平台成熟度，不能把原生 App 的性能结果外推到小程序。 |
| [uni-app](https://uniapp.dcloud.net.cn/) / [uni-app x](https://doc.dcloud.net.cn/uni-app-x/index.html) | 普通版使用 Vue，可交付 App、Web 和微信、支付宝、抖音等多个小程序。x 版采用 uvue / UTS，[小程序编译目标](https://doc.dcloud.net.cn/uni-app-x/mp/index.html)列出微信、支付宝。 | x 版部分 App 代码可[编译为平台语言](https://doc.dcloud.net.cn/uni-app-x/uts/index.html)，具体取决于平台、代码位置和模式；Web 和小程序使用 JavaScript。按[兼容性表](https://doc.dcloud.net.cn/uni-app-x/tutorial/compatibility.html)逐项核对 API、组件和插件，不能用普通版的覆盖范围推断 x 版。 |

- **包体与内存分开看。** 原始比较提到 Tauri「约 3 MB、内存约 40 MB」，缺少设备、构建和进程统计口径，仅作待实测线索。[Tauri 文档](https://v2.tauri.app/start/)给出最小应用可低于 600 KB 的示例；[Windows 安装指南](https://v2.tauri.app/distribute/windows-installer/)同时说明内置离线 WebView2 安装程序约增加 127 MB。比较时区分应用体积、安装包、安装后的占用和外部依赖下载。Windows 7 不在微软的[当前 WebView2 支持清单](https://learn.microsoft.com/en-us/microsoft-edge/webview2/)内，历史安装方式不能当作长期支持。
- **小程序是独立发布目标。** Electron、Tauri、React Native、Flutter 的主线文档未将微信、支付宝、抖音小程序列为官方交付目标。H5 能打开不等于能发布小程序；第三方移植、H5 嵌入、平台小程序构建应分开评估。项目可以按交付目标拆分 UI，只共享接口定义、业务规则或设计规范。

## 尚存的缺口 / 待研究

- 缺少同等功能、同一目标设备上的可比实测。用正式构建实现一条关键流程（如冷启动 → 登录 → 滚动列表 → 调用设备或支付能力），记录下载与安装体积、从启动到可交互的时间、全应用进程的空闲与交互峰值内存、掉帧及各端特有代码量。桌面端与移动端分组比较，关键性能场景可加入原生实现作为对照。
- 做原型时优先验证最可能阻塞上线的端：老系统或离线安装、低端 Android、鸿蒙 NEXT 专用 SDK，或小程序宿主的权限和审核流程。记录测试日期、框架版本、设备、系统及打包配置，方便下一次复用结论。

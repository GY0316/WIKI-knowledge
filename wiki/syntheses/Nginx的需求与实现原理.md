# Nginx 的需求与实现原理

## 问题 / 主题

两条视频各讲了 Nginx 的一半，需要合成一份**需求结论**：

- 第一条（[[抖音-Nginx控制入口层（2026-11）]]）讲**部署形态**：后端本来能直连，为什么还要在前面加一层——统一 TLS、静态与 API 分流、多实例负载分发。
- 第二条（[[抖音-Nginx为什么快（2026-11）]]）讲**并发模型**：为什么一个 worker 能接住一万个慢连接，而一万个进程接不住；以及为什么必须挡在后端前面。

单独看任何一条都会得到片面结论：只看第一条，会以为"小项目不需要"；只看第二条，会以为"所有后端都必须加"。合起来才有判断力。

## 结论

**Nginx 要满足的需求只有两类，且优先级不同：容量需求是刚性的，部署需求是渐进的。**

一句话：**容量需求决定"必须加"，部署需求决定"值得加"，两者都不成立才"可以不加"。**

| 优先级 | 需求 | 触发条件 | 判断结果 |
|---|---|---|---|
| 刚性 | 不让后端的并发容量被慢连接耗尽 | 后端是同步阻塞模型（一连接一进程/线程，如 gunicorn `sync`、PHP-FPM、Apache prefork） | **必须加**，否则弱网用户和慢攻击会直接打穿服务 |
| 渐进 | 对外只暴露一个入口、证书集中、静态分流、多实例分发 | 多服务、多域名、多实例、静态资源量大 | **值得加**，属于横切职责的收敛 |
| — | 两者都不成立 | 后端异步（asyncio/Node/Go）+ 单实例 + 低流量 + 框架自带 HTTPS 与静态 | **可以不加**，直连是对的 |

## 论证 / 对比

### 1. 根需求：C10K 与"等待"的定价

一台机器怎么同时接住一万个连接。在"一连接一进程"模型里，连接的存活时间等于进程的占用时间——**连接很便宜，进程很贵，两者被绑死**，于是慢连接（弱网、长驻页面、故意慢发数据的攻击）可以用极低成本占住极贵的资源。

一次实测里，被抓的那个进程 8 秒中只有 0.16 毫秒在真正读数据，其余时间全在睡觉。**问题不是"处理不过来"，是"睡觉的过程也占着一个进程"。**

所以根需求不是"更快"，而是**把等待从进程里剥离出来**，让容量不再由进程数决定。

### 2. 需求清单：11 条需求与实现手段

表中"来源"标注 v1（部署形态）与 v2（并发模型）；标"补充"的是视频未讲、但同一层常见的职责。

| # | 需求 | 来源 | Nginx 的实现 | 验收信号 |
|---|---|---|---|---|
| R1 | 慢连接不得耗尽服务容量 | v2 | epoll 就绪列表 + 非阻塞 + 少量 worker | 压入 1 万慢连接后，新请求仍能进入 |
| R2 | 单机万级并发，内存可控 | v2 | 一个连接占一块内存，不占进程 | 1 万连接的内存增量在百 MB 量级 |
| R3 | 用满多核 | v2 | 一核一个 worker | `nproc` 与 worker 数一致 |
| R4 | 改配置不停服 | v2 | master 校验配置 → 起新 worker → 旧 worker 排空退出 | 大文件下载中 reload 不中断、字节完整 |
| R5 | 对外只暴露一个入口 | v1 | 反向代理，后端退回内网 | 后端端口不对公网开放 |
| R6 | 证书集中管理 | v1 | 入口做 TLS 终止 | 多服务共用一份证书，续期只改一处 |
| R7 | 静态与业务分流 | v1 | `location` 按路径路由 | 静态请求不占应用进程 |
| R8 | 多实例分发 | v1 | upstream 轮询 / 加权 / `least_conn` | 加机器时对外地址不变 |
| R9 | 慢请求不打到后端 | v2 | 缓冲请求，收齐请求头后才转发 | 后端 worker 不被慢连接占住 |
| R10 | 重复读不回源 | 补充 | `proxy_cache` | 缓存命中率可观测 |
| R11 | 入口可观测 | 补充 | access/error log、状态接口 | 能按状态码与上游分桶排查 |

R1–R4 是**内部机制**（为什么它扛得住）；R5–R9 是**对外价值**（为什么该放在最前面）；R10–R11 是**运营必需**，视频没讲但绕不开。

### 3. 关键机制：四句话解释"为什么快"

1. **一个 worker 用 epoll 管上万个连接，从不干等**：连接登记一次，内核把有数据的放进就绪列表，进程只处理就绪的；半行数据先记下就走。
2. **一核一个 worker，共用 master 打开的端口**：master 先 `listen` 再 `fork`，子进程天然继承同一个监听套接字；或用 `reuseport` 让每个 worker 各开一个、由内核分发。
3. **master 管配置与进程，reload 不断连接**：新 worker 接班，旧 worker 不再接新连接，处理完手上请求才退出。
4. **放在最前面做反向代理，替后端挡住慢连接**：请求头收齐才转发，后端只处理"已经准备好"的请求。

### 4. 与后端的耦合：并发模型决定"需不需要"

这是两条视频合起来最有价值的判断，也是原始材料里最容易漏掉的一句：

- **同步阻塞后端必须加**。实测 4 个 gunicorn `sync` worker 直接吃 1000 个慢连接，新请求 10 次全部超时；前面加一层后 29 次全部进入。gunicorn 自己的文档就写明"强烈建议放在代理服务器后面，且强烈建议 Nginx"。
- **异步后端不是"必须"，但仍常常"值得"**。asyncio/Node/Go 自带非阻塞事件循环，容量问题可以自己扛；但 TLS 集中、静态分流、灰度切流、统一限流这些横切职责依然会重复，只是从"刚性"降为"渐进"。

换句话说：**Nginx 挡的不是"流量"，是"不完整的请求"和"不属于业务的那部分工作"。**

### 5. 边界：它不是魔法

- Apache 后来也有事件驱动的 `event` MPM——**这是模型之争，不是厂商之争**。
- Caddy（Go）：每连接一个 goroutine，起步几 KB，底层等数据仍走 epoll；1 万慢连接 212 MB 也能全接住，且证书自动申请续期，配置更少。
- Cloudflare 早年靠 Nginx，2022 年起自研 Pingora（Rust）。
- 结论：**"少量进程 + 事件驱动 + 非阻塞"是这一类组件的共同解**，Nginx 是其中生态最成熟、运维资料最多的一个实现，不是唯一解。

### 6. 两条视频的分工

| | 视频一 | 视频二 |
|---|---|---|
| 回答 | 要不要加这一层 | 它凭什么扛得住、为什么必须在后端前面 |
| 视角 | 部署形态（南北向入口） | 并发模型（连接与进程解绑） |
| 关键判据 | 证书 / 静态 / 多实例，三选一 | 后端是否一连接一进程 |
| 共同结论 | Nginx 是"可控入口层"，不是必需品 | 同一个结论的机制解释 |

两者合起来的完整表述：**Nginx 是一个用"少量事件驱动进程"替后端承接"慢、碎、非业务"请求的可控入口层；容量需求让它必须存在，部署需求让它值得存在。**

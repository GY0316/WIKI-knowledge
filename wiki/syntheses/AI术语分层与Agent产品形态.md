# AI 术语分层与 Agent 产品形态

## 问题 / 主题

AI 时代的术语——LLM、多模态、Agent、Codex、本地智能体、VSCode + Agent、虾测等——之所以让人混乱，是因为它们不在同一个层面：有的是技术组件，有的是能力或工程概念，有的是产品形态，还有的是岗位。本文按“模型层 → 能力层 → 产品层 → 岗位层”归纳，并给出网页对话框、Claude Code CLI、Claude Desktop 的辨析框架。

## 结论

1. **先分层再比较**。跨层比较是术语混乱的主要来源：拿模型和产品比“强弱”，拿协议和岗位比“前景”，都得不出有效结论。
2. **Agent 的判定只有一条**：把人拿掉之后，它能不能自己决定下一步，并根据执行结果调整。拆成三个必要条件：LLM 在做决策、有工具能改变环境、有循环和状态，缺一不可。
3. **Workflow 与 Agent 的分界是“路径谁定”**：人预先编排步骤是 workflow，模型运行时决定步骤是 agent。工程上 workflow 更可靠、更便宜、更好调试；真正的自主 agent 只该用在路径无法预先枚举的任务上。
4. **泛用性不来自多 agent 串联**，来自工具覆盖面、上下文工程和错误恢复能力。多 agent 只在并行、上下文隔离、权限或人格隔离三类场景值得用。
5. **产品差异可用三轴定位**：模型在哪（这些产品大多在云端）、工具在哪执行、谁决定下一步。网页版、CLI、Desktop 不是替代关系，是同一个模型的不同“身体”。

## 论证 / 对比

### 一、模型层：零件

这一层基本只需“知道它是什么”，日常工作很少直接操作。

| 术语 | 实际含义 |
|---|---|
| LLM（大语言模型） | 根据上文预测下一个 token 的概率模型。三个关键特征：无状态、无记忆（除非写回去）、无行动能力（只能输出文字） |
| 多模态 | 能处理文本以外的模态。注意区分“输入多模态、输出文本”与真正的“输入输出全模态” |
| Token / 上下文窗口 | token 是计费和信息处理的最小单位；上下文窗口是模型同时能“看见”的上限，也是 agent 时代最稀缺的资源 |
| 推理模型（reasoning model） | 先“想”再答，用 test-time compute 换准确率；o 系列、Claude 的 extended thinking 属此类 |
| 预训练 / 后训练 / SFT / RLHF | 先大规模读语料，再用人类偏好或可验证奖励（RLVR）让它“听话、会做题” |
| 幻觉 / RAG / 微调 / Embedding / 蒸馏 / 量化 / MoE | 分别是：编造事实；外挂检索；改模型权重；把文本变成向量；大模型教小模型；压缩模型；混合专家（省算力） |

### 二、能力层：从“会说”到“会做”

这是术语最密集、最容易被营销词搞乱的一层。

#### Agent 的定义

> **Agent = 模型 + 工具 + 循环 + 停止条件。**

三个必要条件，缺一不可：

1. 有 LLM 在做决策，而不是按固定代码跑。
2. 有工具或环境（文件系统、终端、浏览器、API）让它能真正改变世界。
3. 有循环和状态，能连续跑很多步，直到成功或耗尽预算。

#### Workflow 与 Agent

| 维度 | Workflow | Agent |
|---|---|---|
| 路径由谁定 | 人预先写好的代码路径 | 模型运行时动态决定 |
| 模型角色 | 只负责其中每一步 | 决定流程、工具和停止时机 |
| 可靠性 | 高，可测试、可预测、成本可控 | 低一些，难测试、难控成本 |
| 适用 | 步骤可以枚举 | 路径无法预先枚举 |

这个区分来自 Anthropic 2024 年底的 *Building effective agents*，现在已是业界共识。市面上大量叫“Agent”的东西，其实是 workflow 加一点自主性。这不是好坏问题：工程上 workflow 更可靠、更便宜、更好调试；真正的自主 agent 只该用在开放决策空间，写操作还应加人工确认。

#### 其余核心词

| 术语 | 含义 |
|---|---|
| Tool use / Function calling | 模型输出“调用某函数 + 参数”，外部执行后把结果喂回去；agent 出现的技术前提 |
| ReAct | Reason + Act 交替，最经典的 agent 循环范式 |
| Memory | 短期在上下文里，长期在外部存储或向量库 |
| Reflection | 让模型回看自己的输出并修正 |
| Subagent / Handoff | 主 agent 派生子 agent 干活，或把任务交接给专门的 agent |
| HITL（human in the loop） | 关键动作前需要人批准，例如删除文件、付款 |
| MCP（Model Context Protocol） | Anthropic 2024 年开源的工具接入标准，相当于 agent 世界的 USB-C；OpenAI、Google 等已支持，“支持 MCP”约等于“能插任意工具” |
| A2A | agent 与 agent 之间的通信协议，Google 提出，已交给 Linux 基金会 |
| Orchestration（编排） | 决定多个 agent、工具、步骤怎么配合；常见模式有 supervisor-worker、pipeline、路由、并行、辩论 |
| Context engineering | 2025 年后逐渐取代“提示词工程”的说法：决定什么信息在什么时刻进入上下文，包括裁剪、压缩、检索、摘要、工具描述 |
| Harness / Scaffold | 包在模型外面的工程代码。同一个模型换个 harness，效果天差地别，这是 agent 产品真正的竞争力 |
| Eval / Trace / 护栏 | 评测集衡量好不好、链路追踪看清每步干了什么、权限/沙箱/审批防止乱来 |

### 三、产品层：同一个东西的不同封装

按“谁在驾驶”排序，能一眼看出谱系：

| 形态 | 谁做决定 | 典型代表 |
|---|---|---|
| 代码补全 | 人，AI 猜下一行 | 早期 Copilot |
| 对话框 | 人问，AI 答，不改环境 | ChatGPT、豆包 |
| Chat-in-IDE | 人主导，AI 生成片段供复制 | Cursor Tab、Copilot Chat |
| Agent in IDE | AI 主导，人审 diff | Cursor Agent、Cline、Copilot agent mode |
| CLI / 本地 agent | AI 主导，在你机器上动手 | Claude Code、Codex CLI、Aider |
| 云端 / 后台 agent | AI 异步自主，人验收 | Codex cloud、Devin |

### 四、具体产品辨析

**VSCode + Agent**：把 agent 装进编辑器。价值不在编辑器本身，而在于编辑器天然提供了 agent 的“手脚”：文件系统、终端、语言服务器（LSP）、diff 审阅、git。这些是纯 chatbot 没有的。本质是“给 agent 一个能干活的工作台”。

**Codex 的词义变迁**：

- 2021 年的 Codex：一个代码模型（code-davinci），初代 Copilot 的底座，2023 年已下线。
- 2025 年后的 Codex：OpenAI 的软件工程 agent 产品（CLI + 云端），与当年的模型不是一回事。

同一个名字指了两个不同层次的东西。遇到这类词，先问“说的是模型还是产品”。

**本地智能体（local agent）**：对比的是云端 agent。

- 本地：跑在自己的机器上，能读本地文件、跑本地命令、连本地 MCP 服务。隐私好、延迟低、能碰真实环境；但吃本地算力，状态可能随进程消失。
- 云端：跑在隔离容器里，克隆仓库来干活。不占本地机器、可并行、能长任务异步跑；但碰不到本地私有数据和工具。

Claude Code 两边都有，Codex 也是 CLI + cloud 双形态。选择本质是在“环境可达性”和“隔离/并行”之间取舍。

**workbody**：整理稿按 CodeBuddy（腾讯的 AI 编程工具）理解，与 Cursor 同一生态位：IDE 外壳 + 多模型接入 + agent 能力 + 企业内网适配。差异化通常不在模型，而在上下文工程、工具生态和私有化部署。**该词义待核实**。

**虾测**：整理稿按 LobstestAI 理解。如果它把测试相关工具（浏览器驱动、脚本执行、断言、报告生成）封装成 LLM 可调用的工具集，再让模型自己规划测试步骤，那它是一个**领域 agent（domain agent）**。按三条件判断：模型做决策、工具有动手能力、循环能连跑，三者成立才算是 agent。它更像“把 agent 开发这件事本身产品化”——提供 harness + 工具集 + 编排层，让用户描述目标、agent 去完成，而不是“让 agent 开发工程师手工编排一个通用 agent”。**产品边界待核实**。

### 五、“编排成泛用性较强的 agent”的误解

泛用性不来自“把多个 agent 串起来”，而来自三件事：

1. 工具的覆盖面。
2. 上下文工程的功力。
3. 出错后能不能恢复。

多 agent 编排本身不产生泛用性，反而增加不确定性和调试成本。实践中，一个强 agent 加一套好工具，通常打得过三个弱 agent 互相传话。多 agent 真正值得用的场景只有三类：

- 子任务可以并行（各查各的）。
- 子任务上下文要隔离（互相污染会变傻）。
- 子任务需要不同的权限或人格（一个只读、一个能写）。

这里还有一个根本张力：**泛用性和可靠性天然对立**。领域 agent（工具集限定、路径收敛）就是比通用 agent 好用、稳定——这不是妥协，是设计选择。虾测如果定位在测试领域，那“泛用”应指“覆盖各种测试场景”，而不是“什么都能干”。

### 六、岗位层

| 岗位 | 实际工作 |
|---|---|
| Prompt engineer | 岗位名基本已被吸收，实际工作改名为 context engineer |
| AI 应用工程师 / LLM 应用开发 | 写 harness、接工具、做 RAG、搭评测 |
| Agent 工程师 | 不训练模型；设计循环、定义工具接口、做上下文管理、写评测、设护栏、压成本和延迟。核心是系统设计 + 对模型能力边界的直觉，不是机器学习 |
| AI Infra | 推理部署、GPU、并发、KV cache |
| AI 产品经理 | 判断“这件事该不该做成 agent” |

回到“虾测是不是 agent 开发工程师做的工作”：**是，但更准确地说，它是把这类工作封装成了产品。** 做出它的人在做 agent 工程；用它的人在做“用 agent 解决测试问题”，两者技能要求不同。

### 七、网页对话框 vs Claude Code CLI vs Claude Desktop

三个最容易被误解的点是：它们的模型都跑在云端。“本地”的从来不是模型，是工具和文件。

三个坐标轴：

| 轴 | 问的问题 |
|---|---|
| ① 模型在哪 | 云端 API。三个场景都一样（除非本地跑 Ollama 之类） |
| ② 工具在哪执行 | 浏览器沙箱？你的机器？还是云容器？ |
| ③ 谁决定下一步 | 人一步步问，还是模型自己循环？ |

第③轴决定它是聊天还是 agent；第②轴决定它能改变什么。

#### 1. 网页对话框（claude.ai、ChatGPT 网页版）

一句话：一个隔着玻璃的聪明同事。你能给它看东西，它碰不到你的桌子。

- 能碰到：云端沙箱（代码执行、文件上传分析）、联网搜索、远程 MCP 连接器、artifacts（就地渲染网页/图表）。
- 碰不到：本地文件、终端、内网系统。
- 交互：一问一答，上下文靠人搬运——贴什么它才看得到什么。
- 状态：会话级，关掉就散（除非产品做了记忆功能）。
- 隐性成本是“上下文的搬运费”：任务一长，人就成了人肉数据总线。
- 优势：零安装、跨设备、随手可用、结果好分享。

#### 2. Claude Code CLI

一句话：坐到你电脑旁边的实习生，手能碰到键盘。

- 能碰到：整个本地文件系统（限授权目录）、shell、git、本地 MCP 服务、真实开发环境。
- 交互：给目标不给步骤。它自己读文件、改代码、跑测试、看报错、再改，循环到通过。
- 权限：默认每次工具调用要批准，可配置白名单或完全放开。
- 形态：终端程序，能管道、能写进脚本、能进 CI（headless 模式）。
- 和网页版的真正差别不是“云 vs 本地”，而是：问答 vs 行动；沙箱 vs 真实环境。后者正是它必须有权限审批层的原因。

#### 3. Claude Desktop

一句话：玻璃上开了一扇门。还是聊天框，但能伸手到本地。

- 一个聊天窗口：功能上接近网页版。
- 一个本地 MCP 宿主：这是关键增量。网页版只能连远程 MCP，桌面版能启动本机 MCP 进程，读本地文件、连本地数据库、操作本地应用。
- 系统级能力：截图、剪贴板、选中文字直接发、全局快捷键。
- 界面里通常也能直接开 Claude Code 会话，所以“桌面版 vs CLI”在能力上越来越重叠，差别退化成用鼠标还是用键盘。

#### 横向对比

| 维度 | 网页对话框 | Claude Code CLI | Claude Desktop |
|---|---|---|---|
| 模型 | 云端 | 云端 | 云端 |
| 工具执行地 | 浏览器/云沙箱 | 你的机器 | 你的机器（经本地 MCP） |
| 碰本地文件 | 否 | 是 | 是（需配 MCP） |
| 自主循环 | 弱（一问一答） | 强（目标驱动） | 聊天弱，内嵌 Code 强 |
| 上下文谁搬 | 人 | 它自己读 | 人 / 它 |
| 风险等级 | 低（可重开） | 高（能删文件） | 中高 |
| 适合谁 | 所有人 | 工程师 | 想用本地工具的非工程用户 |
| 典型任务 | 问概念、分析上传文件、写一段代码 | 改仓库、跑测试、批量重构 | 查本地文档、连内网系统、日常问答 |

#### 它们不是替代关系

它们是同一个模型的不同“身体”：

- 网页版给的是**可达性**（任何设备、零配置）。
- CLI 给的是**行动力**（真环境、可循环、可脚本化）。
- Desktop 给的是**本地工具 + 图形界面的交集**（不用记命令也能碰到本地东西）。

选型不是“哪个更强”，而是“这次任务需要它碰到什么”：

- 只需要它知道 → 网页版。
- 需要它动手改你的仓库 → CLI。
- 需要它碰到本地的非代码资源（文档库、内网、本地数据库）但不想开终端 → Desktop。

还有一个第四形态：**云端 agent**（Claude Code on the web、Codex cloud 那类）。它用同一套 harness，只是把执行环境从“你的机器”换成“克隆了你仓库的云容器”。于是产品差异可以写成一个乘法式：

> 同一套 agent 逻辑 × 不同的执行环境（浏览器沙箱 / 你的机器 / 云容器）× 不同的入口（网页 / 终端 / 桌面）

### 八、防忽悠三问

看到一个新名词，问三句就能定位：

1. **它是模型、工具、协议，还是产品？**（不同层的东西经常被混着比较）
2. **它是 workflow 还是 agent？**（路径是人定的还是模型定的）
3. **它自己决定下一步吗？能动手吗？能连跑很多步吗？**（三问全 yes 才是 agent）

## 尚存的缺口 / 待研究

- 虾测 / LobstestAI 的产品边界是“领域 Agent 产品”还是“通用 Agent 编排平台”，目前按目录名和描述推断，未核实。
- “workbody”按 CodeBuddy 理解，词义待确认；同类产品（Warp、Trae、通义灵码）的差异也未展开。
- A2A 与 MCP 的分工、生态成熟度和实际采用情况缺少一手资料。
- 本地 agent 与云端 agent 的权限模型、数据边界和成本结构需要实测对比。
- 岗位市场数据（title 口径、能力要求、薪资区间）缺少真实 JD 样本。

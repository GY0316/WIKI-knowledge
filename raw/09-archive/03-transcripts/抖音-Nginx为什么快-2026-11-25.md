# 抖音「一万个接不住，一个全接住」ASR 原文

00:00~00:06	一万个接不住，一个全接住？左边一万个进程在干活，还是接不住，右边只有一个，全接住了。
00:07~00:14	它叫 Nginx，淘宝、京东、小红书，响应头里的 Server 写的都是它或者它的改版。
00:16~00:23	2002 年，伊戈尔・赛索耶夫开始写它。要解决一道题：一台服务器怎么同时接住一万个连接？这道题叫 C10K。
00:25~00:33	先看老办法：来一个连接就派一个进程专门守着，直到它断开。Apache 的 prefork 模式就是这样。
00:33~00:45	麻烦出在慢连接上。信号差的手机开着不关的网页，还有故意慢慢往外挤的攻击。我抓了其中一个进程 8 秒，读数据只用了 0.16 毫秒，剩下的时间全在睡觉。
00:46~00:59	等它的下一行，我在一台 12 核的 Linux 上放进来一万个这样的慢连接，每个每 5 秒才发一行。Apache 默认最多 256 个进程，一下就被占满。新请求试了 20 次，一次都没进来。
01:01~01:20	那就给它一万个。它真开出了 10001 个进程，一万个干活的加一个管事的全在睡觉，各等各的连接。光这些进程就吃掉 1.1GB 内存，一万个全占满以后再来新请求还是进不去。连接越多，进程越多。这条路走到一万就走不动了。右边那一个进程是怎么接住一万个连接的？
01:23~01:38	最直接的想法：挨个问一遍，谁有数据了？早年的 select 和 poll 就是这样，每次把所有连接交给内核，挨个查一遍。一万个查一圈，有数据的往往就那几个，其余都白查。
01:39~01:58	Linux 后来给了新办法，叫 event poll，简称 epoll。连接只登记一次，哪个来了数据，内核就把它放进就绪列表。进程醒来，只看这张列表，处理完接着睡。还有一条：它从不干等，数据只来了半行，就先记下，转身去处理别的连接。
01:59~02:05	GET /Logo.png HTTP/1.1，这叫非阻塞。一个连接只占它一小块内存，不占一个进程。Nginx worker 就是这样一个进程。
02:08~02:22	同样一万个慢连接，Nginx 只有两个进程，一个 worker，一个 worker，一共 112MB。新请求 59 次，全进来了。我把这个 worker 抓了 3 秒，它醒了 1032 次，每次平均拿到 6 个连接，没有一次空手。整台机器的 CPU 只忙了 2%。
02:26~02:32	要是连上以后什么都不发。一万个空闲连接，Nginx 只多占 5.6MB，Apache 要 1.5GB。
02:34~02:42	一个进程同一时刻只能用一个 CPU 核。这台机器 12 个核，Nginx 就开 12 个 worker，一核一个。
02:42~03:03	问题来了，12 个 worker 守着同一个 8080 端口，为什么不冲突？你先想两秒，因为端口只打开了一次，打开它的不是 worker，是 master。master 先打开 8080，再 fork 出 12 个 worker。fork 出来的子进程，天生就拿着同一个监听套接字。看这台机器：8080 上只有一行 LISTEN，13 个进程拿的都是 5 号文件描述符。
03:08~03:18	新连接进来，内核只叫醒其中一个 worker 去接，还可以开 reuseport。Listen 8080 reuseport；每个 worker 各开一个监听套接字，12 个监听套接字，各用各的。ss 里变成 12 行 LISTEN，由内核来分。
03:18~03:37	master 自己不处理请求，它读配置、开端口、管 worker，哪个挂了就补一个。它最拿手的是改配置不断连接，执行 reload。master 先检查新配置，再按新配置开一批新 worker，旧 worker 不再接新连接。把手上的请求处理完，再退出。
03:38~03:47	我一边下载一个 40MB 的文件，一边 reload 了 3 次：下载没断，下完一个字节不差。换成先停再启，下载当场断在 17.7MB。
03:49~03:56	讲到这儿就明白，为什么几乎每个网站都把它放在最前面。你写的后端很多就是一个连接一个进程。比如 Python 常用的 gunicorn 默认的 sync worker。
04:01~04:14	一个请求从头占到尾，我给它 4 个 worker 直接放进 1000 个慢连接，新请求 10 次全部超时。前面挡一个 Nginx，慢连接都停在它这儿，它把整个请求头收齐才转给后端，新请求 29 次全进来了。
04:15~04:32	gunicorn 的文档自己就写着强烈建议放在代理服务器后面，而且强烈建议用 Nginx，这就叫反向代理。站在后端前面替它接请求，后端就是后厨，闲人免进。
04:33~04:44	这个合集叫后厨重地，讲的就是守在后厨门口的东西，顺手还能把请求分给好几台后端，这叫负载均衡。把结果存一份，下回直接返回，这叫缓存。
04:46~05:02	二十多年过去，W3Techs 统计 30.1% 的网站还在用它，排第一的是 Cloudflare 自己的服务器，33%。Cloudflare 早年也靠 Nginx，2022 年说已经长得比它大了，自己写了 Pingora。
05:03~05:22	我自己这两年用的是 Caddy：Go 写的，配置几行，HTTPS 证书自动申请、自动续。它给每个连接一个 goroutine，看着像又回到了一个连接一个，可 goroutine 起步只有几 KB，底下替它们等数据的还是 epoll（原字幕作 "易破"，按上下文校正）。同样 10000 个慢连接，它一个进程 212MB，新请求也全进来了。
05:23~05:33	Apache 后来也有了事件驱动的 event 模式，所以 Nginx 这一整套都是从一个问题里长出来的，别让慢连接占住进程。
05:33~05:50	面试被问 Nginx 为什么快，就答四句：一个 worker 用 epoll 管上万个连接，从不干等。一核一个 worker，共用 master 打开的端口，master 管配置和进程，reload 不断连接，放在最前面做反向代理，替后端挡住慢连接。
05:51~05:58	你现在用 Nginx 还是 Caddy？评论区说说为什么。

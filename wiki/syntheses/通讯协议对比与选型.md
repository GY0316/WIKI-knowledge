# 通讯协议对比与选型

## 问题 / 主题

REST、SOAP、gRPC、GraphQL、Webhook、WebSocket、WebRTC 常被并列讨论，但它们并不在同一层：前四者是接口范式，Webhook 是回调通知模式，WebSocket 是全双工传输通道，WebRTC 是实时媒体与 P2P 协议族。本文先建立分层认知，再逐项给出通讯格式、代码案例和使用注意点，最后补齐容易遗漏的通用协议与选型矩阵。

## 结论

1. **先分层再选型**。请求-响应接口、服务端推送、全双工通道、实时媒体、消息中间件解决的是不同问题，不能只按“性能高低”排序。
2. **七个协议之外还缺常用通道**：SSE、JSON-RPC 2.0、MQTT、AMQP、Kafka、STOMP、tRPC、WebTransport，以及作为底座的 HTTP/2 与 HTTP/3。
3. **协议只是外壳**。超时、重试、幂等、鉴权、契约版本、可观测性这六件事没设计好，换任何协议都会出事；HTTP 契约与 Webhook 投递的治理细节见 [[API交互面与契约治理]]。

## 论证 / 对比

### 0. 分层

| 层 | 协议/范式 | 本质 | 谁主动 |
|---|---|---|---|
| 传输底座 | TCP/UDP、TLS、HTTP/1.1、HTTP/2、HTTP/3(QUIC) | 字节怎么搬 | — |
| 请求-响应接口 | REST、SOAP、gRPC、GraphQL、JSON-RPC、tRPC | 一次调用换一次结果 | 客户端 |
| 服务端推送 | Webhook、SSE | 事件发生就通知 | 服务端 |
| 全双工通道 | WebSocket | 一条长连接双向发消息 | 双方 |
| 实时媒体/P2P | WebRTC | 音视频与数据直连 | 双方 |
| 消息中间件 | MQTT、AMQP、Kafka、STOMP、NATS | 解耦、缓冲、多消费者 | 发布方 |

### 1. REST

**定位**：Fielding 2000 年提出的架构风格，不是协议。落地形态是“HTTP 动词 + 资源 URL + JSON”，无状态、可缓存、统一接口。优势是通用性：任何语言、网关、浏览器都支持。

**通讯格式**：

```http
GET /v1/parts/P-2026-00123 HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOi...
Accept: application/json
If-None-Match: "v12"
```

```http
HTTP/1.1 200 OK
Content-Type: application/json
ETag: "v13"
Cache-Control: private, max-age=60

{"part_no":"P-2026-00123","name":"前副车架","status":"active","version":"B"}
```

```http
POST /v1/test-orders HTTP/1.1
Content-Type: application/json
Idempotency-Key: 5b0f3c1e-7a2d-4c9e-9f10-2d6a8b7c4e21

{"part_no":"P-2026-00123","items":["salt-spray","vibration"]}
```

```http
HTTP/1.1 201 Created
Location: /v1/test-orders/TO-2026-0001

{"order_no":"TO-2026-0001","status":"accepted"}
```

**代码案例**：

```python
from fastapi import FastAPI, Header, HTTPException, Path
from pydantic import BaseModel

app = FastAPI()

class OrderIn(BaseModel):
    part_no: str
    items: list[str]

@app.get("/v1/parts/{part_no}")
def get_part(part_no: str = Path(pattern=r"^P-\d{4}-\d{5}$")):
    part = repo.find(part_no)
    if not part:
        raise HTTPException(404, {"code": "PART_NOT_FOUND", "message": part_no})
    return {"part_no": part.no, "name": part.name, "status": part.status}

@app.post("/v1/test-orders", status_code=201)
def create_order(body: OrderIn, idempotency_key: str = Header(...)):
    # 同一 Idempotency-Key 重试返回同一结果，而不是创建两单
    order = repo.create_once(body, key=idempotency_key)
    return {"order_no": order.no, "status": order.status}
```

**注意点**：

- 状态码不要一律 200。`201` 配 `Location`、`204` 无正文、`409` 冲突、`422` 校验失败、`429` 限流；错误体用稳定的 `code` 字段，别让调用方解析 `message`。[[API交互面与契约治理]] 3.3 节列过这个坑。
- 幂等性：GET/PUT/DELETE 应幂等，POST 不幂等。下单、创建委托这类写操作必须带 `Idempotency-Key`，服务端去重。
- 分页用游标，少用大 offset；深分页时数据库要扫描掉前面所有行。
- 版本与兼容：URL major 版本、字段级 deprecated、Sunset 头；新增可选字段兼容，新增必填、删字段、改类型都是破坏性变更。规则见 [[API交互面与契约治理]] 第十节。
- 超时与重试：只重试幂等请求，指数退避 + jitter，避免故障时制造重试风暴。
- 缓存：善用 `ETag`/`If-None-Match`、`Cache-Control`；带用户身份的响应别被公共 CDN 缓存。
- 认证信息别放 query，会进访问日志、浏览器历史和 Referer。
- REST 不适合服务端主动推送，硬做只能轮询；要推送换 SSE、WebSocket 或 Webhook。

### 2. SOAP

**定位**：基于 XML 的消息协议，靠 WSDL 描述契约，配套 WS-* 标准（WS-Security、WS-Addressing、WS-ReliableMessaging）。通常跑在 HTTP POST 上，也能走 SMTP/TCP。主要存在于银行、电信、ERP、政务等存量系统。

**通讯格式**：

```http
POST /PartService HTTP/1.1
Content-Type: text/xml; charset=utf-8
SOAPAction: "urn:parts:GetPart"
```

```xml
<?xml version="1.0"?>
<soap:Envelope xmlns:soap="http://www.w3.org/2003/05/soap-envelope">
  <soap:Header>
    <auth:Token xmlns:auth="urn:parts">Bearer ...</auth:Token>
  </soap:Header>
  <soap:Body>
    <p:GetPart xmlns:p="urn:parts">
      <p:partNo>P-2026-00123</p:partNo>
    </p:GetPart>
  </soap:Body>
</soap:Envelope>
```

失败用 `Fault`，不是 HTTP 状态码：

```xml
<soap:Fault>
  <soap:Code><soap:Value>soap:Sender</soap:Value></soap:Code>
  <soap:Reason><soap:Text xml:lang="zh">零件不存在</soap:Text></soap:Reason>
  <soap:Detail><errorCode>PART_NOT_FOUND</errorCode></soap:Detail>
</soap:Fault>
```

WSDL 是契约的核心：

```xml
<definitions targetNamespace="urn:parts" xmlns:tns="urn:parts">
  <portType name="PartPort">
    <operation name="GetPart">
      <input message="tns:GetPartRequest"/>
      <output message="tns:GetPartResponse"/>
    </operation>
  </portType>
</definitions>
```

**代码案例**：客户端用 `zeep` 最省事，WSDL 自动生成调用桩。

```python
from zeep import Client, Settings

client = Client(
    "https://erp.example.com/PartService?wsdl",
    settings=Settings(strict=False, xml_huge_tree=False),
)
part = client.service.GetPart(partNo="P-2026-00123")
print(part.name, part.status)
```

服务端通常用 Apache CXF（Java）、WCF（.NET）或 Spyne（Python），新项目一般不会从零写 SOAP 服务。

**注意点**：

- XXE 攻击：解析 XML 前必须禁用 DTD 和外部实体，这是 SOAP 接口最常见的安全漏洞。
- 错误在 Fault 里：HTTP 可能返回 500，也可能某些实现返回 200 但 Body 是 Fault，调用方必须解析正文判断成功与否。
- 命名空间极其敏感：前缀变化、`mustUnderstand` 处理不当都会导致解析失败；用 QName 而不是字符串匹配。
- WS-Security 成本高：证书、签名、加密、时间戳，配置错一点就全部失败；排障要抓完整 XML。
- 负载重、解析慢：移动端和前端不友好；附件用 MTOM/XOP，别 base64 塞进 XML。
- 互操作性：不同厂商对 WS-* 的实现有差异，联调以双方 WSDL 和实际报文为准。
- 新项目不要选，除非对接方只提供 SOAP。封装老 SOAP 服务时参考 [[API交互面与契约治理]] 的 ACL 防腐层，把 XML、字段名和错误码挡在适配器里。

### 3. gRPC

**定位**：Google 的 RPC 框架，HTTP/2 + Protocol Buffers，IDL 先行。支持一元、服务端流、客户端流、双向流四种形态。强类型、二进制、高性能，适合内部服务间通信和多语言团队。

**通讯格式**：

```proto
syntax = "proto3";
package parts.v1;

service PartService {
  rpc GetPart (GetPartRequest) returns (Part);
  rpc WatchOrders (WatchRequest) returns (stream OrderEvent);
}

message GetPartRequest { string part_no = 1; }

message Part {
  string part_no = 1;
  string name = 2;
  optional string drawing_no = 3;
  PartStatus status = 4;
}

enum PartStatus {
  PART_STATUS_UNSPECIFIED = 0;
  ACTIVE = 1;
  OBSOLETE = 2;
}
```

线上不是 JSON，而是 HTTP/2 帧里的 Protobuf 二进制：

```text
:method: POST
:path: /parts.v1.PartService/GetPart
content-type: application/grpc
te: trailers
grpc-timeout: 2S

[1 字节压缩标志][4 字节大端长度][Protobuf 字节]
```

响应在 HTTP/2 trailers 里带 `grpc-status: 0`、`grpc-message`。

**代码案例**：

```python
import grpc
from concurrent import futures
import parts_pb2, parts_pb2_grpc

class PartService(parts_pb2_grpc.PartServiceServicer):
    def GetPart(self, request, context):
        part = repo.find(request.part_no)
        if part is None:
            context.abort(grpc.StatusCode.NOT_FOUND, "part not found")
        return parts_pb2.Part(part_no=part.no, name=part.name, status=part.status)

server = grpc.server(futures.ThreadPoolExecutor(max_workers=8))
parts_pb2_grpc.add_PartServiceServicer_to_server(PartService(), server)
server.add_insecure_port("[::]:50051")
server.start()
server.wait_for_termination()
```

```python
import grpc
from parts_pb2 import GetPartRequest
from parts_pb2_grpc import PartServiceStub

with grpc.insecure_channel("localhost:50051") as channel:
    stub = PartServiceStub(channel)
    part = stub.GetPart(GetPartRequest(part_no="P-2026-00123"), timeout=2)
    print(part.name)
```

**注意点**：

- 浏览器不直接支持：浏览器拿不到 HTTP/2 trailers，需要 gRPC-Web 或 Connect 做转换，通常还要代理。
- 字段编号是契约：已用编号不能复用、不能改类型；删字段要 `reserved`；枚举必须有 `0 = UNSPECIFIED`。
- proto3 默认值不序列化：`0`、`""`、`false` 和“没设置”在线上无法区分；需要区分时用 `optional` 或 wrapper 类型。
- deadline 必须传：客户端设 `timeout`，服务端继续往下游传；不设超时，一个慢依赖能把整条链路拖死。
- 长连接与负载均衡：四层 LB 会把连接固定到少数实例；用客户端负载均衡、服务网格或 L7 代理。
- 错误模型：别只返回 `INTERNAL` + 字符串；用 `google.rpc.Status` + `details` 携带结构化错误码和字段。
- 消息大小：默认 4MB 上限，大对象用 streaming 或对象存储引用。
- 调试成本：二进制报文，需要 `grpcurl`、反射服务、拦截器日志，比 curl 麻烦。
- 移动网络：连接切换、NAT 超时会断流，需要重连和重试策略。
- 对外接口慎用：公网、合作伙伴、浏览器场景，REST/JSON 的通用性更值钱。

### 4. GraphQL

**定位**：查询语言 + 运行时。单一端点，客户端声明要哪些字段，服务端按 schema 解析。解决 REST 的 over-fetching / under-fetching 和多次往返问题，适合前端需求多变、后端聚合多个服务的 BFF 层。

**通讯格式**：

```graphql
type Query {
  part(partNo: ID!): Part
}

type Part {
  partNo: ID!
  name: String!
  status: PartStatus!
}

enum PartStatus { ACTIVE OBSOLETE }
```

```http
POST /graphql HTTP/1.1
Content-Type: application/json

{
  "query": "query($no: ID!) { part(partNo: $no) { partNo name status } }",
  "variables": { "no": "P-2026-00123" },
  "operationName": "GetPart"
}
```

```json
{
  "data": {
    "part": { "partNo": "P-2026-00123", "name": "前副车架", "status": "ACTIVE" }
  }
}
```

出错时通常仍是 HTTP 200，错误在 `errors` 里：

```json
{
  "data": { "part": null },
  "errors": [
    { "message": "part not found", "path": ["part"], "extensions": { "code": "PART_NOT_FOUND" } }
  ]
}
```

**代码案例**：Python 用 Strawberry。

```python
import strawberry
from strawberry.fastapi import GraphQLRouter
from fastapi import FastAPI

@strawberry.type
class Part:
    part_no: str
    name: str
    status: str

@strawberry.type
class Query:
    @strawberry.field
    def part(self, part_no: str) -> Part | None:
        p = repo.find(part_no)
        return Part(p.no, p.name, p.status) if p else None

schema = strawberry.Schema(query=Query)
app = FastAPI()
app.include_router(GraphQLRouter(schema), prefix="/graphql")
```

**注意点**：

- N+1 是头号问题：每个字段一个 resolver，列表里每条记录再查一次库。用 DataLoader 批量合并，或预加载关联。
- 查询复杂度和深度要限制：客户端能任意嵌套，恶意查询能把服务打挂；做 depth limit、cost 分析、超时、持久化查询。
- HTTP 缓存失效：单一 POST 端点让 CDN/浏览器缓存很难做；查询用 GET + 持久化查询 ID，或自己加缓存层。
- 权限要落到字段级：隐藏字段不等于没权限，resolver 必须逐个校验，否则可通过嵌套查询绕过。
- 错误语义：GraphQL 习惯 200 + `errors`，HTTP 状态码只表达传输层失败；监控要解析 `errors`，不能只看状态码。
- 版本策略：通常不做 URL 版本，靠字段 `@deprecated` 渐进淘汰；破坏性变更要协调所有客户端。
- 生产环境关 introspection 或加鉴权，别把完整 schema 暴露给外部。
- 文件上传：GraphQL 的 multipart 上传规范已不推荐，用预签名 URL 直传对象存储。
- 别为简单 CRUD 硬上 GraphQL：收益来自“客户端自定义字段”和“多服务聚合”，单资源接口用 REST 更简单。
- 订阅：`subscription` 需要 WebSocket 或 SSE 承载，扩展时同样要考虑 pub/sub 和连接数。

### 5. Webhook

**定位**：反向 API / HTTP 回调。注册一个 URL，事件发生时对方 POST 过来。它不是某个 RFC 协议，而是建立在 HTTP + 一套约定（签名、重试、幂等）之上的模式。适合跨组织、低频、事件驱动的通知。

库内已有较完整的设计参考：[[API交互面与契约治理]] 8.3 节（订阅注册、签名头、重试规则）与 6.5 节（对方没有事件能力时的替代方案）。

**通讯格式**：

```http
POST /v1/subscriptions
Content-Type: application/json

{
  "event_types": ["TestOrderAccepted", "ReportApproved"],
  "callback_url": "https://partner.example.com/hooks/test-center",
  "secret": "whsec_...",
  "active": true
}
```

```http
POST /hooks/test-center HTTP/1.1
Content-Type: application/json
X-Event-Id: 0f5c1f5e-3f0a-4b7e-9f2a-6d1c8e4b9a10
X-Event-Type: TestOrderAccepted
X-Event-Version: 1
X-Timestamp: 1763949120
X-Signature: sha256=...

{"event_id":"0f5c1f5e-...","event_type":"TestOrderAccepted","data":{"order_no":"TO-2026-0001","status":"accepted"}}
```

**代码案例**：发送方签名。

```python
import hashlib, hmac, json, time, requests

body = json.dumps({"event_id": "evt_1", "event_type": "TestOrderAccepted",
                   "data": {"order_no": "TO-2026-0001"}})
ts = str(int(time.time()))
mac = hmac.new(b"whsec_...", f"{ts}.{body}".encode(), hashlib.sha256).hexdigest()

requests.post(
    "https://partner.example.com/hooks/test-center",
    data=body,
    headers={"Content-Type": "application/json",
             "X-Timestamp": ts,
             "X-Signature": f"sha256={mac}"},
    timeout=5,
)
```

接收方校验：

```python
import hashlib, hmac, time, json
from fastapi import FastAPI, Header, HTTPException, Request

app = FastAPI()
SECRET = b"whsec_..."

@app.post("/hooks/test-center")
async def receive(request: Request,
                  x_timestamp: str = Header(...),
                  x_signature: str = Header(...)):
    raw = await request.body()
    if abs(time.time() - int(x_timestamp)) > 300:          # 5 分钟时间窗，防重放
        raise HTTPException(401, "stale timestamp")
    mac = hmac.new(SECRET, f"{x_timestamp}.".encode() + raw, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(f"sha256={mac}", x_signature):
        raise HTTPException(401, "bad signature")
    await enqueue(json.loads(raw))                          # 先入队，快速返回 2xx
    return {"ok": True}
```

**注意点**：

- 必须验签 + 时间窗：用 `hmac.compare_digest` 常量时间比较；只验签不验时间戳仍可被重放。
- 至少一次投递：重试会产生重复，接收方按 `event_id` 幂等，不要假设“只来一次”。[[API交互面与契约治理]] 7.5 节也强调这一点。
- 快速返回：接收端在 2xx 前做重活会超时并触发重试；正确做法是落库/入队后立刻返回。
- 区分可重试与永久失败：5xx/超时重试，4xx（除 408、429）视为永久失败并累计停用。
- 顺序不保证：带序号或 `aggregate_version`，消费方按版本丢弃旧事件。
- SSRF 防护：回调 URL 必须校验，禁止内网地址、元数据地址，最好 allowlist + 域名验证。
- 公网可达性：对方防火墙、IP 白名单、TLS 证书都要提前确认；必要时提供轮询对账兜底。
- 事件会丢：Webhook 没有 retention/replay，必须配套投递日志、重放 API 和定期对账。
- 别拿 Webhook 当消息队列：扇出大、内部服务多、需要 replay 时用 Kafka/RabbitMQ；选型对比见 [[API交互面与契约治理]] 8.1。

### 6. WebSocket

**定位**：RFC 6455，基于 TCP 的全双工长连接。先用 HTTP Upgrade 握手，之后在同一连接上双向收发文本/二进制帧。适合聊天、协同编辑、实时行情、游戏等低延迟双向场景。

**通讯格式**：

```http
GET /ws/orders HTTP/1.1
Host: api.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
```

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

```text
FIN(1) RSV(3) opcode(4) | MASK(1) payload_len(7/16/64) | [mask key 4B] | payload
opcode: 0x1 text, 0x2 binary, 0x8 close, 0x9 ping, 0xA pong
```

客户端到服务端的帧必须掩码；服务端到客户端不掩码。

**代码案例**：浏览器客户端。

```js
const ws = new WebSocket("wss://api.example.com/ws/orders");

ws.onopen = () => {
  ws.send(JSON.stringify({ type: "subscribe", topic: "TestOrderAccepted" }));
};
ws.onmessage = (e) => {
  const msg = JSON.parse(e.data);
  console.log(msg.type, msg.data);
};
ws.onclose = (e) => {
  console.warn("closed", e.code, e.reason);
  setTimeout(connect, Math.min(30000, 1000 * 2 ** retries++)); // 指数退避重连
};
```

Node 服务端（`ws`）：

```js
const { WebSocketServer } = require("ws");
const wss = new WebSocketServer({ port: 8080, path: "/ws/orders" });

wss.on("connection", (ws, req) => {
  ws.isAlive = true;
  ws.on("pong", () => (ws.isAlive = true));
  ws.on("message", (raw) => {
    const msg = JSON.parse(raw);
    if (msg.type === "subscribe") subscribe(ws, msg.topic);
  });
  ws.send(JSON.stringify({ type: "hello", serverTime: Date.now() }));
});

setInterval(() => {
  wss.clients.forEach((ws) => {
    if (!ws.isAlive) return ws.terminate();
    ws.isAlive = false;
    ws.ping();
  });
}, 30000);
```

**注意点**：

- 没有自动重连和心跳：协议层有 ping/pong，但浏览器 API 不暴露发送 ping；业务层要自己做心跳、超时判断、指数退避重连，并在重连后重新订阅。
- 代理和负载均衡会掐空闲连接：Nginx/ELB 默认 60 秒左右超时，心跳间隔要小于它。
- 水平扩展难：连接是有状态的，多节点之间要靠 Redis Pub/Sub、Kafka 或 NATS 广播消息；粘性会话只能解决一半问题。
- 消息语义要自己定义：WebSocket 只保证帧顺序，不保证断线重连后消息不丢；重要消息要带序号、ACK、去重和补拉。
- 背压：慢消费者会把发送缓冲撑爆；要设缓冲上限、丢弃策略或断开会话。
- 鉴权：别把 token 放 query string（日志泄露）；用 Cookie、首帧认证或 `Sec-WebSocket-Protocol` 携带；同时校验 `Origin` 防 CSRF。
- 安全：生产必须 `wss://`；限制单帧大小、消息频率；压缩（permessage-deflate）有 CPU 放大风险。
- 移动端：切后台、网络切换会断连，恢复后要重新同步状态。
- 不要拿它替代 REST：请求-响应语义要自己造 correlation id，普通 CRUD 用 HTTP 更省心。

### 7. WebRTC

**定位**：W3C/IETF 的实时通信协议族，目标是浏览器之间直连传输音视频和数据。核心组件：ICE（STUN/TURN 穿透）、DTLS（密钥协商）、SRTP（媒体加密）、SCTP（DataChannel）、拥塞控制与编解码协商。它不规定信令，信令要自己搭。

**通讯格式**：WebRTC 没有单一的报文格式，而是三段：

1. 信令（自定义，通常 WebSocket/HTTP）：交换 SDP offer/answer 和 ICE candidate。
2. SDP：描述媒体能力，文本格式。

```text
v=0
o=- 4611731400430051336 2 IN IP4 127.0.0.1
s=-
t=0 0
a=group:BUNDLE 0 1
m=audio 9 UDP/TLS/RTP/SAVPF 111
a=rtpmap:111 opus/48000/2
m=video 9 UDP/TLS/RTP/SAVPF 96
a=rtpmap:96 VP8/90000
```

3. 媒体/数据：DTLS-SRTP 加密的 RTP 包，或 SCTP 上的 DataChannel；底层 UDP，经 ICE 选出的候选地址对传输。

**代码案例**：浏览器端，信令通道用 WebSocket 示意。

```js
const pc = new RTCPeerConnection({
  iceServers: [
    { urls: "stun:stun.example.com:3478" },
    { urls: "turn:turn.example.com:3478", username: "u", credential: "p" },
  ],
});

pc.onicecandidate = (e) => {
  if (e.candidate) signaling.send({ type: "candidate", candidate: e.candidate });
};
pc.ontrack = (e) => {
  remoteVideo.srcObject = e.streams[0];
};

const localStream = await navigator.mediaDevices.getUserMedia({ audio: true, video: true });
localStream.getTracks().forEach((t) => pc.addTrack(t, localStream));

// 主叫
const offer = await pc.createOffer();
await pc.setLocalDescription(offer);
signaling.send({ type: "offer", sdp: pc.localDescription });

// 被叫收到 offer 后
await pc.setRemoteDescription(offer);
const answer = await pc.createAnswer();
await pc.setLocalDescription(answer);
signaling.send({ type: "answer", sdp: pc.localDescription });

// 双方收到远端 candidate
await pc.addIceCandidate(candidate);

// 数据通道（可选）
const dc = pc.createDataChannel("chat", { ordered: false, maxRetransmits: 0 });
dc.onmessage = (e) => console.log(e.data);
```

**注意点**：

- 信令必须自建：WebRTC 规范故意不定义信令；用 WebSocket 最方便，但要自己处理房间、鉴权、离线、重连。
- NAT 穿透不是百分百：STUN 能解决大多数家庭网络，对称 NAT/企业防火墙必须靠 TURN 中继；TURN 带宽成本高，要就近部署。
- UDP 被封就废：企业网络常封 UDP，TURN 要支持 TCP/TLS 443 回落。
- 安全：媒体强制 DTLS-SRTP；信令层要鉴权，SDP 和 candidate 都来自不可信端，服务端不要盲目信任。
- 多人不要用 mesh：N 个参与者两两连接是 N² 路流，3 人以上就该上 SFU（LiveKit、mediasoup、Janus）或 MCU。
- 自适应：带宽、分辨率、码率要联动；用 simulcast/SVC 适配弱网。
- 浏览器策略：`getUserMedia` 需要 HTTPS（localhost 例外）、用户手势触发播放、设备权限被拒要有降级。
- 移动端：切后台停流、网络切换触发 ICE restart、耗电和发热明显。
- 排障：`chrome://webrtc-internals` + `getStats()` 看 candidate pair、丢包、抖动、码率；ICE 失败先查 TURN 和防火墙。

### 8. 容易遗漏的通用协议

| 协议 | 定位 | 格式/模型 | 什么时候用 |
|---|---|---|---|
| SSE (Server-Sent Events) | 服务器→客户端单向推送，跑在 HTTP 上 | `text/event-stream`，`data:`/`event:`/`id:` 行 | LLM 流式输出、进度、通知；比 WebSocket 简单，自动重连 |
| JSON-RPC 2.0 | 轻量 RPC 信封，传输无关 | `{"jsonrpc":"2.0","id":1,"method":"...","params":{}}` | MCP、LSP、以太坊；[[API交互面与契约治理]] 第四节即此格式 |
| MQTT | 物联网发布/订阅，broker 模式 | 二进制报文，topic + QoS 0/1/2 | 设备上报、低带宽、海量连接 |
| AMQP / RabbitMQ | 企业消息队列 | exchange/queue/binding + ack | 任务队列、灵活路由、延迟队列 |
| Kafka 协议 | 分布式日志/流平台 | topic/partition/offset/consumer group | 高吞吐事件流、回放、多消费者 |
| STOMP | 简单文本消息协议，常跑在 WebSocket 上 | `SEND`/`SUBSCRIBE`/`MESSAGE` 帧 | 浏览器接入消息 broker |
| tRPC | TypeScript 端到端类型安全 RPC | 基于 HTTP，类型从服务端推导 | 全栈 TS 单体/小团队，开发体验优先 |
| WebTransport | HTTP/3(QUIC) 上的双向传输 | 流 + 数据报 | 替代 WebSocket 做低延迟游戏/直播，仍在普及 |
| HTTP/2 / HTTP/3 | 传输层演进 | 多路复用、头部压缩；QUIC 基于 UDP | 所有现代 Web 流量的底座 |
| 长轮询 (long polling) | 客户端拉模式的推送兜底 | 挂起请求直到有数据或超时 | 不支持 SSE/WebSocket 的老环境 |

SSE 的最小案例，与 LLM 流式输出直接相关：

```python
from fastapi.responses import StreamingResponse
import asyncio, json

async def event_stream():
    yield "retry: 3000\n\n"
    for i, chunk in enumerate(generate_chunks()):
        yield f"id: {i}\nevent: delta\ndata: {json.dumps({'text': chunk}, ensure_ascii=False)}\n\n"
        await asyncio.sleep(0)

@app.get("/v1/answers/stream")
def stream():
    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

```js
const es = new EventSource("/v1/answers/stream");
es.addEventListener("delta", (e) => append(JSON.parse(e.data).text));
es.onerror = () => { /* EventSource 会自动重连，带 Last-Event-ID */ };
```

SSE 的注意点：浏览器同域 HTTP/1.1 下并发连接数有限（约 6 条）；`EventSource` 不能自定义请求头，鉴权用 Cookie 或把 token 放 query（注意日志）；断线重连靠 `Last-Event-ID` 续传，服务端要支持。

### 9. 选型矩阵

| 需求 | 首选 | 备选/说明 |
|---|---|---|
| 对外开放 API、简单 CRUD | REST + OpenAPI | 契约进仓库，CI 做 breaking check |
| 内部服务高性能调用、多语言 | gRPC | 浏览器场景加 gRPC-Web/Connect |
| 前端字段需求多变、聚合多个服务 | GraphQL（BFF） | 简单 CRUD 别用 |
| 服务端通知外部合作方 | Webhook | 签名、重试、幂等、对账 |
| 浏览器实时双向 | WebSocket | 只需服务端推送时优先 SSE |
| 音视频、屏幕共享、P2P 数据 | WebRTC | 多人上 SFU，备 TURN |
| 异步解耦、削峰、多消费者 | Kafka/RabbitMQ | 内部事件；Outbox 方案见 [[API交互面与契约治理]] |
| IoT/弱网设备 | MQTT | QoS 按场景选 |
| LLM 流式输出 | SSE | 比 WebSocket 简单，天然走 HTTP |
| Agent 工具调用 | MCP（JSON-RPC） | 报文细节见 [[API交互面与契约治理]] |

### 10. 跨协议共性

协议只是外壳，以下六件事在选任何协议前都要先设计：

- **超时**：每一跳都要有 deadline，不能让默认无限等待。
- **重试**：只重试幂等操作，指数退避 + jitter，设最大次数。
- **幂等**：写操作带幂等键，消费方按事件 ID 去重。
- **鉴权**：传输层 TLS 之上还要有身份与权限；token 不进日志和 query。
- **契约版本**：OpenAPI/WSDL/proto/schema 进仓库，CI 做破坏性检查与代码生成；规则见 [[API交互面与契约治理]] 第十节。
- **可观测性**：trace_id 贯穿调用链，事件带 correlation_id 与 causation_id，投递失败要能看到死信与重放。

## 尚存的缺口 / 待研究

- 七种协议在具体项目中的性能基准（延迟、吞吐、连接数）缺少实测数据；需要搭最小环境压测，而不是引用二手结论。
- WebRTC 的 STUN/TURN 部署与 SFU/MCU 选型尚未展开，需要单独的资料与实验。
- MQTT、AMQP、Kafka 的可靠性与顺序语义只给了定位，没有系统对比投递模型、分区策略和运维成本。
- SSE 在 HTTP/2 下的连接数行为、与 HTTP/3 的配合，需要查规范与实测确认。

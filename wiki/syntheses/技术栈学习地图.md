# 技术栈学习地图

> 全库的**学习路线总入口**。每个技术方向一份独立的技能树报告，本页只做索引、共性方法与扩容规则，不复制正文。
> 新增方向时只改本页一行 + 新建一份报告，其余结构不动。

## 问题 / 主题

学习类内容容易变成两种情况：要么散落在若干篇文章里，找不到入口；要么全塞进一个大而全的文档，越长越没人读。

本页解决的是结构问题：**一份地图 + 每个方向一份独立报告**。三份已有报告（后端、Agent、前端）都遵循同一套骨架，因此：

- 查找时先来这张地图，再进具体方向；
- 阅读时可以在不同方向之间对照同一层级（地基 / 核心 / 工程化 / 业务）；
- 扩容时照抄骨架，不需要重新设计文档结构。

## 结论

1. **一方向一页，一页一骨架**。方向之间只通过「映射章节」和双链发生关系，不互相复制内容。
2. **共用的不是知识点，是方法论**：四层一轴、五档掌握度、项目阶梯、验收四问、模块页索引。这套方法决定了报告之间可以横向比较。
3. **总目录只增不改**：新增方向是加一行；已建页面的状态从「规划」变「已建」，章节结构不变。
4. **地图不承担教学**。它回答「先看哪份、按什么顺序看、下一步写哪页」，不回答「某个知识点是什么」。

## 三、共用方法论

三份报告刻意使用同一套结构，目的是让它们可以横向对照。

### 3.1 四层一轴

| 层 | 回答的问题 | 后端 | Agent | 前端 |
|---|---|---|---|---|
| 地基 | 不变的原理 | 语言/数据/网络/OS | 后端底座 + 模型 API | HTML/CSS/JS/浏览器 |
| 核心 | 这个方向的看家本领 | 工程素养与框架 | 工具/上下文/循环/RAG | 组件/状态/数据/表单 |
| 工程化 | 能不能上线并维护 | 测试/交付/可观测 | 评测/护栏/成本/长任务 | 构建/测试/性能/安全 |
| 业务 | 该不该做、怎么验收 | 系统设计与边界 | 适用性与 ROI | 管理台模式与体验 |

一条**主轴**（具体技术栈）只在该方向的页内展开，不进入总目录。

### 3.2 五档掌握度

| 档位 | 含义 | 验证方式 |
|---|---|---|
| 知道 | 听过名词 | 能说出它解决什么问题 |
| 会用 | 照文档能跑 | 能独立完成日常任务 |
| 懂原理 | 知道为什么 | 能解释机制与边界 |
| 能排障 | 出问题能定位 | 能给出排查路径与修复 |
| 能设计 | 能做取舍 | 能选型、能画图、能说明代价 |

面试通常考后三档，升职只看后两档。

### 3.3 三个通用判据

任何一块知识该不该现在学，问三句：

1. 它能不能扩大你**排障时的可选动作**？
2. 它能不能扩大你**设计时的可选方案**？
3. 不学它，会不会**卡住当前的交付**？

前两条都不满足、第三条也不满足的，进「暂缓」。

### 3.4 落地四件套

每份报告都必须有：

- **五档自测**：每块知识至少 3 个问题，答不上就是没到那一档。
- **项目阶梯**：5 个左右递进项目，每个都有验收标准。
- **模块页索引**：10–20 个待写页面，带优先级与依赖。
- **缺口登记**：本页写不清的地方，如实列出并进 `gaps.md`。

### 3.5 验收四问

学完一块，自我检验：

1. **能讲清**：三句话向非同行解释。
2. **能画图**：能画出它在系统里的位置与数据流。
3. **能排障**：能列出三种常见故障与定位步骤。
4. **能选型**：能在两个方案之间说出取舍与适用条件。

## 五、扩容规则：新增一个技术栈

照做五步，不需要重新设计：

1. **复制骨架**：frontmatter（`title` / `type: synthesis` / `date` / `tags` / `sources`）+ 章节序列。
2. **定四层**：这个方向的地基、核心、工程化、业务分别是什么；写不出来的层，说明该方向还没想清楚。
3. **定判据**：三条该方向特有的判断标准（例如 Agent 是「路径可枚举 / 有可验证反馈」，前端是「三态齐全 / 键盘可达」）。
4. **写自测与阶梯**：每块五档自测，5 个项目带验收标准。
5. **建索引并登记**：10–20 个模块页；回填本页状态、`index.md`、`log.md`。

**命名约定**

- 技术方向：`<方向>技能树`，如 `前端技能树`、`数据工程技能树`。
- 岗位方向：`<岗位>技能树`，如 `Agent开发工程师技能树`。
- 文件名即双链名，全库唯一；规划中的页面只写普通文字，不写成双链，避免死链。

**必填章节**

`问题 / 主题` → `结论` → `全景（四层一轴）` → 四个分层章节 → `与相邻方向的映射` → `成长路径` → `项目阶梯` → `学习方法与反模式` → `索引表` → `引用的页面` → `外部参考` → `尚存的缺口`

**可选章节**：岗位分层（岗位类报告）、面试与简历、案例拆解。

## 六、规划中的方向（优先级与触发信号）

| 方向 | 为什么会需要 | 触发信号 | 与现有页面的关系 |
|---|---|---|---|
| 数据工程 | 测试数据、指标、报表会越积越多 | 出现「同一指标两个数」或报表需求排队 | 复用后端的数据设计；可连 [[DDD模块边界与数据协作]] 的数据所有权 |
| 测试开发 | 自动化与质量度量是独立技能 | 手工回归成为发布瓶颈 | 与 [[测试业务链的Agent落点]] 相邻 |
| SRE / DevOps | 部署、容量、故障管理需要体系 | 上线频率上升或故障复盘重复出现 | 复用后端的可观测性与容器章节 |
| 移动端 | 若业务需要现场采集或移动审批 | 出现移动端需求 | 与前端共享工程化方法 |
| ML 工程 | 模型训练与推理是另一套工程 | 需要自研模型而非调用 API | 与 Agent 页的「模型素养」衔接 |
| 安全工程 | 攻击面随系统复杂度上升 | 合规要求或安全事件 | 复用后端的 API 安全章节并向下展开 |

## 七、维护约定

- 新增或完成一个模块页时，**只改三处**：该方向报告的状态列、`index.md`、`log.md`；本页只在方向级别变化时改。
- 本页的「总目录」是唯一权威列表；其他页面提到方向时链接这里，不各自维护清单。
- 方向之间的顺序不代表学习顺序；顺序由「怎么用这张地图」和个人目标决定。
- 报告过期（超过一年未更新、技术栈已变）时，在标题下标注日期，不删除旧内容。
